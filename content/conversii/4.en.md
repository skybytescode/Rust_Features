# Conversions and dynamic types — Expert

Where exactly coercions happen, how deref interacts with method resolution, how `TypeId` is implemented, and why some `From` implementations are impossible.

## Coercion sites

Coercions happen only at **coercion sites**, where the compiler already knows the expected type:

- the arguments of a function or method;
- `let` with an explicit type, `static` and `const`;
- the fields in struct expressions (`Struct { field: value }`);
- the value returned by a function;
- the elements of an array, when the array's type is known.

When the expected type is **not** known, but has to be inferred, no coercion applies. The most common case is a generic parameter with a trait constraint:

```rust,compile_fail
trait Sum {
    fn sum(&self) -> i32;
}

impl Sum for &[i32] {
    fn sum(&self) -> i32 { self.iter().sum() }
}

fn total<T: Sum>(x: T) -> i32 { x.sum() }

fn main() {
    let a: &[i32] = &[1, 2, 3];
    println!("{}", total(a));          // OK
    println!("{}", total(&[1, 2, 3])); // error E0277: T is inferred as &[i32; 3], no coercion
}
```

To make it compile, you do the coercion explicitly at the call site: `total(&[1, 2, 3][..])` or `total(&[1, 2, 3] as &[i32])`.

## Unsizing for your own types

`Box<T>` → `Box<dyn Trait>` works thanks to the unstable `CoerceUnsized` trait, implemented for `Box`, `Rc`, `Arc`, `&T` and the other standard pointers. On stable you can't implement it for your own smart pointer. You can, however, unsize a struct whose **last** field is a generic type:

```rust
struct Tagged<T: ?Sized> {
    id: u32,
    value: T,
}

fn main() {
    let concrete: Box<Tagged<[u8; 4]>> = Box::new(Tagged { id: 1, value: [1, 2, 3, 4] });
    let dynamic: Box<Tagged<[u8]>> = concrete; // unsizing on the last field
    println!("{} {:?} {}", dynamic.id, &dynamic.value, dynamic.value.len());
}
```

## Deref and method resolution

For `x.method()`, the compiler applies `*x`, `**x` and so on in turn, through `Deref`, until it finds the method. The order can be surprising when several layers have methods with the same name:

```rust
use std::rc::Rc;

fn main() {
    let a = Rc::new(vec![1, 2, 3]);
    let b = a.clone();               // Rc::clone: only increments the counter
    let c = (*a).clone();            // Vec::clone: copies the data
    println!("{} {}", Rc::strong_count(&a), c.len());
    let _ = b;
}
```

That's why the recommended convention is `Rc::clone(&a)` instead of `a.clone()`: it makes clear that the pointer is being cloned, not the data.

## `TypeId` and why `Any` requires `'static`

`TypeId::of::<T>()` is a 128-bit identifier, computed by the compiler from a hash of the complete type. `downcast_ref` compares the value's `TypeId` with the requested one:

```rust
use std::any::{Any, TypeId};

fn main() {
    println!("{}", size_of::<TypeId>()); // 16 bytes
    println!("{}", TypeId::of::<Vec<u8>>() == TypeId::of::<Vec<u8>>());
    println!("{}", TypeId::of::<Vec<u8>>() == TypeId::of::<Vec<i8>>());

    let x: &dyn Any = &5_u32;
    println!("{}", x.type_id() == TypeId::of::<u32>());
}
```

Lifetimes are erased before code generation, so `&'a str` and `&'static str` would have the same `TypeId`. If `Any` accepted types with non-`'static` lifetimes, you could downcast from a `&'short T` to a `&'static T` and read freed memory. The `T: 'static` constraint closes that hole.

## Downcasting on your own traits

A `dyn MyTrait` can't be turned directly back into the concrete type. The standard technique is an `as_any` method. Since Rust 1.86, though, there's also direct upcasting from `&dyn MyTrait` to `&dyn Any`, if `Any` is a supertrait:

```rust
use std::any::Any;

trait Component: Any {
    fn name(&self) -> &'static str;
}

struct Button { label: String }
struct Image;

impl Component for Button { fn name(&self) -> &'static str { "button" } }
impl Component for Image { fn name(&self) -> &'static str { "image" } }

fn main() {
    let ui: Vec<Box<dyn Component>> = vec![Box::new(Button { label: "OK".into() }), Box::new(Image)];
    for c in &ui {
        let as_any: &dyn Any = c.as_ref(); // upcasting: dyn Component → dyn Any
        match as_any.downcast_ref::<Button>() {
            Some(b) => println!("{}: {}", c.name(), b.label),
            None => println!("{}", c.name()),
        }
    }
}
```

## Impossible `From` implementations

`impl<T> From<T> for T` (reflexive) and `impl<T, U: From<T>> Into<U> for T` are blanket implementations in the standard library. They rule out certain implementations that look reasonable:

```rust,compile_fail
struct Boxed<T>(T);

// looks natural: any value can go into a box...
impl<T, U: Into<T>> From<U> for Boxed<T> {
    fn from(u: U) -> Self { Boxed(u.into()) }
}
// error E0119: for U = Boxed<T>, it conflicts with `impl<T> From<T> for T`

fn main() {}
```

The usual solution is a method of your own (`Boxed::new(x.into())`) or a concrete implementation for each source type.

> **Key takeaway:** coercions happen only where the expected type is known. Deref applies in a chain, including during method resolution, which is where the `Rc::clone(&x)` convention comes from. `TypeId` is a 128-bit hash of the type, and `Any` requires `'static` because lifetimes are erased. The blanket implementations in `std` forbid some generic `From`s.
