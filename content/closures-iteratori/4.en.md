# Closures and iterators — Expert

What the compiler generates for a closure, how an iterator chain becomes a single loop, and which specialized optimizations exist in the standard library.

## A closure is an anonymous struct

For each closure, the compiler generates an anonymous type. The captured variables become its fields, and the `Fn*` traits are implemented on it. The size of the closure is the size of its captures:

```rust
fn main() {
    let a = 5u8;
    let b = [0u64; 4];
    let s = String::from("x");

    let nothing = || 1;
    let by_ref = || a + 1;              // captures &u8
    let by_value = move || b.len();     // captures [u64; 4]
    let with_string = move || s.len();  // captures String

    println!("{}", size_of_val(&nothing));     // 0
    println!("{}", size_of_val(&by_ref));      // 8: one reference
    println!("{}", size_of_val(&by_value));    // 32
    println!("{}", size_of_val(&with_string)); // 24
    let _ = (nothing(), by_ref(), by_value(), with_string());
}
```

The hand-written equivalent of `by_ref` looks roughly like this. On stable you can't implement the `Fn*` traits yourself, but you can write an equivalent method:

```rust
struct ByRefClosure<'a> {
    a: &'a u8,
}

impl ByRefClosure<'_> {
    // the compiler would generate `impl Fn<()> for ...` with `call(&self)`
    fn call(&self) -> u8 {
        *self.a + 1
    }
}

fn main() {
    let a = 5u8;
    let c = ByRefClosure { a: &a };
    println!("{}", c.call());
}
```

The hierarchy is `Fn: FnMut: FnOnce`. Any `Fn` can also be called where `FnMut` or `FnOnce` is required.

## Coercion to a function pointer

A closure **without captures** is zero-sized and can be converted to `fn`. With captures, the conversion isn't possible, because a function pointer has nowhere to keep the data:

```rust
fn main() {
    let f: fn(i32) -> i32 = |x| x + 1; // OK: no capture
    println!("{}", f(1));
}
```

```rust,compile_fail
fn main() {
    let k = 10;
    let f: fn(i32) -> i32 = |x| x + k; // error E0308: the closure captures `k`
    println!("{}", f(1));
}
```

## How an iterator chain becomes a loop

`v.iter().map(f).filter(g).sum()` builds a nested type of the form `Filter<Map<slice::Iter<T>, F>, G>`, in which the closures are fields with known types. Each `next()` calls `next()` on the inner layer. Because the types are concrete, LLVM inlines everything into a single loop, with no function calls.

Moreover, many adapters override `fold` / `try_fold`. The consuming methods (`sum`, `for_each`, `count`) use **internal iteration**, through `fold`, instead of repeated calls to `next()`. `Chain`, for example, can go through its two halves with two separate loops, without checking at each step which half it is in.

## `TrustedLen` and `collect`

When it knows exactly how many elements an iterator will produce, `collect::<Vec<_>>()` allocates **once** and writes directly, without capacity checks. The information comes from `size_hint()` and the internal `TrustedLen` trait:

```rust
fn main() {
    let it = (0..1000).map(|x| x * 2);
    println!("{:?}", it.size_hint()); // (1000, Some(1000)): exact

    let v: Vec<i32> = it.collect();
    println!("len {}, capacity {}", v.len(), v.capacity()); // no reallocations

    let filtered = (0..1000).filter(|x| x % 3 == 0);
    println!("{:?}", filtered.size_hint()); // (0, Some(1000)): only an upper bound
}
```

## In-place collection

`v.into_iter().map(...).collect::<Vec<_>>()` can **reuse** the original vector's allocation if the resulting type fits in the same space. The optimization is internal and not guaranteed, but you can observe it:

```rust
fn main() {
    let v: Vec<u32> = (0..1000).collect();
    let ptr_before = v.as_ptr() as usize;

    let w: Vec<u32> = v.into_iter().map(|x| x * 2).filter(|x| x % 4 == 0).collect();
    let ptr_after = w.as_ptr() as usize;

    println!("same allocation: {}", ptr_before == ptr_after);
    println!("{}", w.len());
}
```

## `async` closures and capture in the 2024 edition

Since Rust 1.85, closures can be `async`: `async || { ... }`. They implement the `AsyncFn`, `AsyncFnMut` and `AsyncFnOnce` traits, and the returned future can borrow from the closure's captures. With `|| async { ... }`, that wasn't possible. Details in the Async/await chapter.

> **Key takeaway:** a closure is an anonymous struct whose fields are its captures, and its size is the size of the captures. Only closures without captures become `fn`. Iterator chains are made of concrete types, so LLVM inlines them into a loop. `TrustedLen` and in-place collection eliminate needless allocations.
