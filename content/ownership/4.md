# Ownership și borrowing — Expert

Ce face concret compilatorul cu ownership-ul: cum arată un move în cod mașină, cine decide ordinea de `drop` și ce garanții de aliasing dă `&mut` optimizatorului.

## Un move este un `memcpy`

La nivel de mașină, un move copiază biții valorii, iar sursa este considerată neinițializată. Pentru un `String` se copiază doar cele trei cuvinte (pointer, capacitate, lungime), nu și datele din heap. Optimizatorul elimină de obicei copia complet.

Diferența dintre move și `Copy` nu există în codul generat, ci doar în analiza statică: după un move, compilatorul interzice folosirea sursei și nu mai apelează `drop` pe ea.

## Drop flags

Când un move are loc doar pe o ramură, compilatorul nu știe static dacă la finalul scope-ului trebuie apelat `drop`. Inserează atunci un **drop flag**, un boolean ascuns pe stivă:

```rust
fn main() {
    let s = String::from("poate");
    if std::env::args().count() > 5 {
        drop(s); // move doar pe această ramură
    }
    // la final: `drop(s)` se apelează doar dacă flag-ul spune că `s` încă e inițializat
}
```

## Ordinea de drop

Ordinea este definită de limbaj, nu lăsată la latitudinea compilatorului:

- **variabilele locale** se distrug în ordinea **inversă** declarării;
- **câmpurile** unui struct și elementele unui tuplu se distrug în **ordinea declarării**;
- **temporarele** dintr-o expresie se distrug la finalul instrucțiunii. În unele cazuri, de exemplu în condiția unui `match` sau `if let`, trăiesc mai mult.

```rust
struct Zgomot(&'static str);

impl Drop for Zgomot {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

struct Pereche {
    _a: Zgomot,
    _b: Zgomot,
}

fn main() {
    let _x = Zgomot("x");
    let _p = Pereche { _a: Zgomot("p.a"), _b: Zgomot("p.b") };
    let _y = Zgomot("y");
}
// afișează: drop y, drop p.a, drop p.b, drop x
```

## Leak-urile sunt *safe*

Rust nu garantează că `drop` va fi apelat. `std::mem::forget` este o funcție safe, iar un ciclu de `Rc` produce leak fără niciun `unsafe`. Consecința practică: cod `unsafe` corect **nu se poate baza** pe rularea unui destructor pentru a păstra memoria validă. De aceea API-ul vechi `thread::scoped` a fost scos înainte de 1.0 și înlocuit, mai târziu, cu `thread::scope`, care primește o closure.

Pentru a preveni intenționat un drop, folosește `ManuallyDrop<T>`. E alegerea potrivită când preiei controlul asupra momentului distrugerii, de exemplu în structuri de date scrise cu `unsafe`.

## `&mut` înseamnă unicitate garantată

Pentru optimizator, `&mut T` nu e doar „referință care poate modifica”. E o promisiune că nimeni altcineva nu accesează acea memorie cât timp referința e activă. `rustc` transmite promisiunea către LLVM prin atributul `noalias`, care permite optimizări pe care C le obține doar cu `restrict`:

```rust
pub fn aduna_de_doua_ori(a: &mut i32, b: &i32) {
    *a += *b;
    *a += *b; // LLVM poate citi `*b` o singură dată: știe că `a` și `b` nu se suprapun
}

fn main() {
    let mut x = 1;
    aduna_de_doua_ori(&mut x, &10);
    println!("{x}");
}
```

Din același motiv, a crea în `unsafe` două `&mut` către aceeași memorie este **comportament nedefinit**, chiar dacă nu le folosești niciodată simultan în mod vizibil.

## Modelele de aliasing: Stacked Borrows și Tree Borrows

Regulile exacte pentru pointeri brute și referințe din codul `unsafe` sunt încă în curs de formalizare. Cele două modele principale sunt **Stacked Borrows** și succesorul său mai permisiv, **Tree Borrows**. Ambele sunt implementate în **Miri**, interpretorul care detectează comportament nedefinit:

```bash
rustup +nightly component add miri
cargo +nightly miri test
```

## Unde trăiește borrow checker-ul

Verificarea nu se face pe codul sursă, ci pe **MIR** (Mid-level IR), un graf de control simplificat în care fiecare împrumut primește o *regiune*. Analiza calculează în ce puncte ale grafului fiecare împrumut trebuie să fie viu și semnalează conflictele. **Polonius**, viitorul algoritm, reformulează problema în termeni de *origini* (de unde provine fiecare referință) și acceptă programe corecte pe care NLL încă le respinge.

> **De reținut:** ownership-ul nu există la runtime. Este o analiză statică pe MIR, care la final produce drop flags, ordinea de drop și garanții `noalias` pentru optimizator.
