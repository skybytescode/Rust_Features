# Ownership and borrowing — Expert

What the compiler actually does with ownership: what a move looks like in machine code, who decides the `drop` order, and which aliasing guarantees `&mut` gives the optimizer.

## A move is a `memcpy`

At the machine level, a move copies the bits of the value, and the source is considered uninitialized. For a `String`, only the three words (pointer, capacity, length) are copied, not the heap data. The optimizer usually removes the copy entirely.

The difference between a move and `Copy` doesn't exist in the generated code, only in the static analysis: after a move, the compiler forbids using the source and no longer calls `drop` on it.

## Drop flags

When a move happens only on one branch, the compiler doesn't know statically whether `drop` must be called at the end of the scope. It then inserts a **drop flag**, a hidden boolean on the stack:

```rust
fn main() {
    let s = String::from("maybe");
    if std::env::args().count() > 5 {
        drop(s); // move on this branch only
    }
    // at the end: `drop(s)` is called only if the flag says `s` is still initialized
}
```

## Drop order

The order is defined by the language, not left to the compiler:

- **local variables** are destroyed in **reverse** declaration order;
- the **fields** of a struct and the elements of a tuple are destroyed in **declaration order**;
- **temporaries** in an expression are destroyed at the end of the statement. In some cases, for example in the condition of a `match` or `if let`, they live longer.

```rust
struct Noisy(&'static str);

impl Drop for Noisy {
    fn drop(&mut self) {
        println!("drop {}", self.0);
    }
}

struct Pair {
    _a: Noisy,
    _b: Noisy,
}

fn main() {
    let _x = Noisy("x");
    let _p = Pair { _a: Noisy("p.a"), _b: Noisy("p.b") };
    let _y = Noisy("y");
}
// prints: drop y, drop p.a, drop p.b, drop x
```

## Leaks are *safe*

Rust doesn't guarantee that `drop` will be called. `std::mem::forget` is a safe function, and a cycle of `Rc` leaks without any `unsafe`. The practical consequence: correct `unsafe` code **cannot rely** on a destructor running to keep memory valid. That's why the old `thread::scoped` API was removed before 1.0 and later replaced with `thread::scope`, which takes a closure.

To deliberately prevent a drop, use `ManuallyDrop<T>`. It is the right choice when you take control of when destruction happens, for example in data structures written with `unsafe`.

## `&mut` means guaranteed uniqueness

For the optimizer, `&mut T` isn't just "a reference that can modify". It is a promise that nobody else accesses that memory while the reference is alive. `rustc` passes this promise to LLVM through the `noalias` attribute, which enables optimizations that C only gets with `restrict`:

```rust
pub fn add_twice(a: &mut i32, b: &i32) {
    *a += *b;
    *a += *b; // LLVM may read `*b` only once: it knows `a` and `b` don't overlap
}

fn main() {
    let mut x = 1;
    add_twice(&mut x, &10);
    println!("{x}");
}
```

For the same reason, creating in `unsafe` code two `&mut` to the same memory is **undefined behavior**, even if you never visibly use them at the same time.

## Aliasing models: Stacked Borrows and Tree Borrows

The exact rules for raw pointers and references in `unsafe` code are still being formalized. The two main models are **Stacked Borrows** and its more permissive successor, **Tree Borrows**. Both are implemented in **Miri**, the interpreter that detects undefined behavior:

```bash
rustup +nightly component add miri
cargo +nightly miri test
```

## Where the borrow checker lives

The check isn't done on the source code but on **MIR** (Mid-level IR), a simplified control-flow graph in which each borrow gets a *region*. The analysis computes at which points of the graph each borrow must be alive and reports conflicts. **Polonius**, the future algorithm, reformulates the problem in terms of *origins* (where each reference comes from) and accepts correct programs that NLL still rejects.

> **Key takeaway:** ownership doesn't exist at runtime. It is a static analysis on MIR that ultimately produces drop flags, the drop order, and `noalias` guarantees for the optimizer.
