# Variabile și tipuri — Expert

Cum arată tipurile în memorie: mărime, aliniere, cum își rearanjează compilatorul câmpurile și ce valori sunt interzise pentru un tip.

## Mărime și aliniere

Fiecare tip are o **mărime** (câți octeți ocupă) și o **aliniere** (adresa lui trebuie să fie multiplu de acest număr). Mărimea este întotdeauna multiplu de aliniere:

```rust
use std::mem::align_of;

fn main() {
    println!("u8:   {} / {}", size_of::<u8>(), align_of::<u8>());
    println!("u32:  {} / {}", size_of::<u32>(), align_of::<u32>());
    println!("f64:  {} / {}", size_of::<f64>(), align_of::<f64>());
    println!("char: {} / {}", size_of::<char>(), align_of::<char>());
    println!("():   {} / {}", size_of::<()>(), align_of::<()>());
}
```

`()` are mărimea 0. Tipurile de mărime zero (ZST) nu ocupă memorie: un `Vec<()>` nu alocă nimic, iar un `HashMap<K, ()>` este de fapt un set.

Alinierea poate diferi între platforme și chiar între versiuni de compilator. De exemplu, pe x86-64 alinierea lui `i128` a trecut de la 8 la 16 în Rust 1.77, pentru compatibilitate cu C.

## Compilatorul rearanjează câmpurile

Pentru un struct obișnuit (`repr(Rust)`), ordinea câmpurilor în memorie **nu este garantată**. Compilatorul le poate reordona ca să reducă spațiul pierdut la aliniere. Cu `#[repr(C)]` primești ordinea din cod, ca în C:

```rust
#[allow(dead_code)]
struct Liber {
    a: u8,
    b: u32,
    c: u8,
}

#[allow(dead_code)]
#[repr(C)]
struct CaInC {
    a: u8,
    b: u32,
    c: u8,
}

fn main() {
    // De obicei 8: compilatorul pune `a` și `c` unul lângă altul
    println!("repr(Rust): {}", size_of::<Liber>());
    // Garantat 12: a + 3 octeți umplutură + b + c + 3 octeți umplutură
    println!("repr(C):    {}", size_of::<CaInC>());
}
```

Ca regulă: folosește `repr(C)` doar pentru FFI sau când citești/scrii structura direct din memorie.

## Valori invalide și niche optimization

Nu orice combinație de biți e o valoare validă pentru orice tip:

- un `bool` poate fi doar `0` sau `1`;
- un `char` nu poate depăși `0x10FFFF` și nu poate fi în intervalul surogat `0xD800..=0xDFFF`;
- o referință `&T` nu poate fi nulă și trebuie să fie aliniată;
- `NonZeroU32` nu poate fi 0.

A produce o valoare invalidă, chiar și fără să o folosești, este **comportament nedefinit**.

Compilatorul folosește valorile interzise ca „nișe” în care codifică varianta unui enum. Așa `Option` devine gratuit:

```rust
use std::num::NonZeroU32;

fn main() {
    assert_eq!(size_of::<Option<&u8>>(), size_of::<&u8>());        // None = pointer nul
    assert_eq!(size_of::<Option<Box<u8>>>(), size_of::<Box<u8>>());
    assert_eq!(size_of::<Option<NonZeroU32>>(), 4);                // None = 0
    assert_eq!(size_of::<Option<u32>>(), 8);                       // fără nișă: tag separat
    assert_eq!(size_of::<Option<bool>>(), 1);                      // None = 2
    println!("Option nu costă nimic când tipul are o nișă");
}
```

Garanția e oficială pentru referințe, `Box`, `NonNull`, `NonZero*` și pointeri la funcții. Restul sunt optimizări pe care compilatorul le face azi, dar nu le promite.

## Memorie neinițializată

`let x: u32;` fără valoare e permis, dar compilatorul verifică static că nu citești `x` înainte de atribuire. La nivel de `unsafe`, singurul mod corect de a lucra cu memorie neinițializată este `MaybeUninit<T>`:

```rust
use std::mem::MaybeUninit;

fn main() {
    let mut slot = MaybeUninit::<u64>::uninit();
    slot.write(42);
    // SAFETY: am scris o valoare validă pe linia anterioară
    let x = unsafe { slot.assume_init() };
    println!("{x}");
}
```

Vechea funcție `std::mem::uninitialized()` este deprecated: pentru tipuri ca `bool` sau `&T` era UB imediat, pentru că memoria aleatoare nu respectă invarianții tipului.

## Numere reale: NaN și ordinea totală

IEEE 754 are valori speciale: `+0.0` și `-0.0`, infinit și NaN. Din cauza lui NaN (`NaN != NaN`), `f64` implementează doar `PartialEq` și `PartialOrd`, nu `Eq` și `Ord`. De aceea nu poți sorta direct un `Vec<f64>` cu `sort()` și nici nu poți folosi `f64` ca cheie în `HashMap`. Soluția este `total_cmp`, care definește o ordine totală:

```rust
fn main() {
    let nan = f64::NAN;
    println!("NaN == NaN: {}", nan == nan); // false
    println!("0.0 == -0.0: {}", 0.0_f64 == -0.0); // true

    let mut v = vec![3.5, f64::NAN, -1.0, 0.0, -0.0];
    v.sort_by(f64::total_cmp);
    println!("{v:?}"); // [-1.0, -0.0, 0.0, 3.5, NaN]
}
```

## Evaluarea la compilare

Valoarea unui `const` sau `static` se calculează la compilare, de un interpretor din compilator care lucrează pe MIR. Același motor stă și la baza Miri. Poți apela acolo orice `const fn`:

```rust
const fn factorial(n: u64) -> u64 {
    if n == 0 { 1 } else { n * factorial(n - 1) }
}

const F20: u64 = factorial(20); // calculat de compilator, nu la runtime

fn main() {
    println!("{F20}");
}
```

Dacă evaluarea dă overflow sau panic, primești **eroare de compilare**, nu panic la runtime. Blocurile `const { ... }` (Rust 1.79) îți permit să forțezi evaluarea la compilare chiar în mijlocul unei funcții.

> **De reținut:** layout-ul `repr(Rust)` nu e garantat, iar `repr(C)` da. Valorile invalide sunt UB și tot ele fac posibil un `Option` gratuit. `f64` nu are ordine totală fără `total_cmp`, iar `const` rulează cod la compilare.
