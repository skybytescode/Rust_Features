# Variables and types — Expert

What types look like in memory: size, alignment, how the compiler reorders fields, and which values are forbidden for a type.

## Size and alignment

Every type has a **size** (how many bytes it takes) and an **alignment** (its address must be a multiple of this number). The size is always a multiple of the alignment:

```rust
use std::mem::align_of;

fn main() {
    println!("u8:   {} / {}", size_of::<u8>(), align_of::<u8>());
    println!("u32:  {} / {}", size_of::<u32>(), align_of::<u32>());
    println!("f64:  {} / {}", size_of::<f64>(), align_of::<f64>());
    println!("char: {} / {}", size_of::<char>(), align_of::<char>());
    println!("():   {} / {}", size_of::<()>(), align_of::<()>());
}
```

`()` has size 0. Zero-sized types (ZSTs) take no memory: a `Vec<()>` allocates nothing, and a `HashMap<K, ()>` is effectively a set.

Alignment can differ between platforms and even between compiler versions. For example, on x86-64 the alignment of `i128` changed from 8 to 16 in Rust 1.77, for compatibility with C.

## The compiler reorders fields

For an ordinary struct (`repr(Rust)`), the order of fields in memory is **not guaranteed**. The compiler may reorder them to reduce the space wasted on alignment. With `#[repr(C)]` you get the order from the source code, as in C:

```rust
#[allow(dead_code)]
struct Free {
    a: u8,
    b: u32,
    c: u8,
}

#[allow(dead_code)]
#[repr(C)]
struct LikeC {
    a: u8,
    b: u32,
    c: u8,
}

fn main() {
    // Usually 8: the compiler puts `a` and `c` next to each other
    println!("repr(Rust): {}", size_of::<Free>());
    // Guaranteed 12: a + 3 bytes padding + b + c + 3 bytes padding
    println!("repr(C):    {}", size_of::<LikeC>());
}
```

As a rule: use `repr(C)` only for FFI or when you read/write the structure directly from memory.

## Invalid values and niche optimization

Not every bit pattern is a valid value for every type:

- a `bool` can only be `0` or `1`;
- a `char` cannot exceed `0x10FFFF` and cannot be in the surrogate range `0xD800..=0xDFFF`;
- a reference `&T` cannot be null and must be aligned;
- `NonZeroU32` cannot be 0.

Producing an invalid value, even without using it, is **undefined behavior**.

The compiler uses the forbidden values as "niches" in which it encodes an enum's variant. That's how `Option` becomes free:

```rust
use std::num::NonZeroU32;

fn main() {
    assert_eq!(size_of::<Option<&u8>>(), size_of::<&u8>());        // None = null pointer
    assert_eq!(size_of::<Option<Box<u8>>>(), size_of::<Box<u8>>());
    assert_eq!(size_of::<Option<NonZeroU32>>(), 4);                // None = 0
    assert_eq!(size_of::<Option<u32>>(), 8);                       // no niche: separate tag
    assert_eq!(size_of::<Option<bool>>(), 1);                      // None = 2
    println!("Option costs nothing when the type has a niche");
}
```

The guarantee is official for references, `Box`, `NonNull`, `NonZero*` and function pointers. The rest are optimizations the compiler performs today but doesn't promise.

## Uninitialized memory

`let x: u32;` without a value is allowed, but the compiler checks statically that you don't read `x` before it is assigned. In `unsafe` code, the only correct way to work with uninitialized memory is `MaybeUninit<T>`:

```rust
use std::mem::MaybeUninit;

fn main() {
    let mut slot = MaybeUninit::<u64>::uninit();
    slot.write(42);
    // SAFETY: we wrote a valid value on the previous line
    let x = unsafe { slot.assume_init() };
    println!("{x}");
}
```

The old function `std::mem::uninitialized()` is deprecated: for types like `bool` or `&T` it was immediate UB, because random memory does not uphold the type's invariants.

## Floating-point numbers: NaN and total ordering

IEEE 754 has special values: `+0.0` and `-0.0`, infinity, and NaN. Because of NaN (`NaN != NaN`), `f64` implements only `PartialEq` and `PartialOrd`, not `Eq` and `Ord`. That's why you can't sort a `Vec<f64>` directly with `sort()` or use `f64` as a `HashMap` key. The solution is `total_cmp`, which defines a total ordering:

```rust
fn main() {
    let nan = f64::NAN;
    println!("NaN == NaN: {}", nan == nan); // false
    println!("0.0 == -0.0: {}", 0.0_f64 == -0.0); // true

    let mut v = vec![3.5, f64::NAN, -1.0, 0.0, -0.0];
    v.sort_by(f64::total_cmp);
    println!("{v:?}"); // [-1.0, -0.0, 0.0, 3.5, NaN]
}
```

## Compile-time evaluation

The value of a `const` or `static` is computed at compile time by an interpreter inside the compiler that works on MIR. The same engine also underlies Miri. You can call any `const fn` there:

```rust
const fn factorial(n: u64) -> u64 {
    if n == 0 { 1 } else { n * factorial(n - 1) }
}

const F20: u64 = factorial(20); // computed by the compiler, not at runtime

fn main() {
    println!("{F20}");
}
```

If the evaluation overflows or panics, you get a **compile error**, not a runtime panic. `const { ... }` blocks (Rust 1.79) let you force compile-time evaluation even in the middle of a function.

> **Key takeaway:** the `repr(Rust)` layout is not guaranteed, while `repr(C)` is. Invalid values are UB, and they are also what makes a free `Option` possible. `f64` has no total ordering without `total_cmp`, and `const` runs code at compile time.
