# Traits and generics — Advanced

Static vs. dynamic dispatch, associated types, the coherence rules and the "marker" traits through which the compiler checks safety.

## Static vs. dynamic: generics or `dyn Trait`

- **Generics** (`T: Trait`, `impl Trait`) are resolved at compile time. Each type gets its own copy of the function: the call is direct and can be inlined.
- **Trait objects** (`&dyn Trait`, `Box<dyn Trait>`) are resolved at runtime, through a method table (*vtable*). That's how you can put **different** types in the same collection.

```rust
trait Animal {
    fn sound(&self) -> &'static str;
}

struct Cat;
struct Cow;

impl Animal for Cat { fn sound(&self) -> &'static str { "meow" } }
impl Animal for Cow { fn sound(&self) -> &'static str { "moo" } }

fn static_dispatch<A: Animal>(a: &A) -> &'static str {
    a.sound() // compiled separately for Cat and for Cow
}

fn main() {
    println!("{} {}", static_dispatch(&Cat), static_dispatch(&Cow));

    let farm: Vec<Box<dyn Animal>> = vec![Box::new(Cat), Box::new(Cow), Box::new(Cat)];
    for a in &farm {
        print!("{} ", a.sound()); // call through the vtable
    }
    println!();
}
```

## Compatibility with `dyn`

Not every trait can be used as `dyn Trait`. A trait is **dyn-compatible** (formerly: *object safe*) only if none of its methods:

- returns `Self` by value (the size of `Self` isn't known);
- has its own generic parameters (that would need an infinite vtable);
- is an associated function without `self`.

You can exclude them with `where Self: Sized`, so the trait stays usable as `dyn`:

```rust
trait Shape {
    fn area(&self) -> f64;

    fn cloned(&self) -> Self
    where
        Self: Sized; // excluded from the vtable
}

#[derive(Clone)]
struct Square(f64);

impl Shape for Square {
    fn area(&self) -> f64 { self.0 * self.0 }
    fn cloned(&self) -> Self { self.clone() }
}

fn main() {
    let shapes: Vec<Box<dyn Shape>> = vec![Box::new(Square(3.0))];
    println!("{}", shapes[0].area());
    println!("{}", Square(2.0).cloned().area());
}
```

## Associated types vs. generic parameters

`Iterator` has an **associated type**, `type Item`: a type implements `Iterator` only once, with a single `Item`. A generic parameter, as in `From<T>`, allows **several** implementations for the same type:

```rust
struct Counter {
    current: u32,
    up_to: u32,
}

impl Iterator for Counter {
    type Item = u32; // a single element type

    fn next(&mut self) -> Option<u32> {
        if self.current < self.up_to {
            self.current += 1;
            Some(self.current)
        } else {
            None
        }
    }
}

struct Id(u64);
impl From<u32> for Id { fn from(n: u32) -> Self { Id(n as u64) } }
impl From<&str> for Id { fn from(s: &str) -> Self { Id(s.len() as u64) } } // a second implementation

fn main() {
    let sum: u32 = Counter { current: 0, up_to: 4 }.sum();
    println!("{sum} {} {}", Id::from(7_u32).0, Id::from("abc").0);
}
```

## Coherence and the orphan rule

You can implement a trait for a type only if **the trait or the type** is defined in your crate. The rule guarantees there can't be two conflicting implementations in different crates. You can't implement `Display` for `Vec<i32>`, for example, but you can wrap it in a newtype:

```rust
use std::fmt;

struct List(Vec<i32>);

impl fmt::Display for List {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        let texts: Vec<String> = self.0.iter().map(|x| x.to_string()).collect();
        write!(f, "[{}]", texts.join(" | "))
    }
}

fn main() {
    println!("{}", List(vec![1, 2, 3]));
}
```

## Blanket implementations and supertraits

A **blanket** implementation covers every type that meets a condition. A **supertrait** requires one trait to be implemented before another:

```rust
use std::fmt::Display;

trait Label: Display {          // supertrait: whoever implements Label must have Display
    fn label(&self) -> String {
        format!("<{self}>")
    }
}

impl<T: Display> Label for T {} // blanket: every type with Display gets Label

fn main() {
    println!("{} {}", 42.label(), "rust".label());
}
```

The standard library uses this technique everywhere: `impl<T: Display> ToString for T` is why every type with `Display` has `.to_string()`.

## Marker traits: `Send`, `Sync`, `Sized`, `Copy`

Some traits have no methods. They describe a **property** of the type:

| Trait | Means |
|---|---|
| `Send` | the value can be moved to another thread |
| `Sync` | `&T` can be shared between threads |
| `Sized` | the size is known at compile time (implicit on every `T`) |
| `Copy` | copied bit by bit, no move |

`Send` and `Sync` are *auto traits*: the compiler implements them automatically if every field has them. `Rc<T>` isn't `Send`, so the following program doesn't compile:

```rust,compile_fail
use std::rc::Rc;

fn main() {
    let data = Rc::new(5);
    std::thread::spawn(move || {
        println!("{data}"); // error E0277: `Rc<i32>` cannot be sent between threads
    });
}
```

The implicit `Sized` constraint can be relaxed with `?Sized`, so the function also accepts `str`, `[T]` or `dyn Trait` behind a reference:

```rust
use std::fmt::Debug;

fn show<T: Debug + ?Sized>(x: &T) {
    println!("{x:?}");
}

fn main() {
    show("a str");        // T = str, which isn't Sized
    show(&[1, 2, 3][..]); // T = [i32]
}
```

> **Key takeaway:** generics mean static dispatch, and `dyn` means dispatch through a vtable. A trait used as `dyn` can't have generic methods or methods that return `Self`. Associated types allow a single implementation, and the orphan rule prevents conflicts. `Send` and `Sync` are checked automatically.
