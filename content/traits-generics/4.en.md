# Traits and generics — Expert

What a vtable looks like, what monomorphization costs, what GATs are, and how the compiler decides which implementation to use.

## Fat pointers and vtables

A `&dyn Trait` has **two** words: the pointer to the data and the pointer to a static vtable, generated for each (concrete type, trait) pair. The vtable contains, in order:

1. the pointer to `drop_in_place::<T>`;
2. the size of `T`;
3. the alignment of `T`;
4. the pointers to the trait's methods (and those of its supertraits).

The exact layout isn't guaranteed, but this information is accessible through safe APIs:

```rust
use std::fmt::Debug;
use std::mem::{align_of_val, size_of_val};

fn main() {
    let values: [&dyn Debug; 3] = [&1u8, &[0u64; 4], &"text"];
    for v in values {
        // the size and alignment come from the vtable, at runtime
        println!("{v:?}: {} bytes, alignment {}", size_of_val(v), align_of_val(v));
    }
    println!("&dyn Debug: {} bytes", size_of::<&dyn Debug>());
}
```

## Upcasting between trait objects

Since Rust 1.86, a `&dyn Sub` can be converted directly into a `&dyn Super` when `Super` is a supertrait of `Sub`. The subtrait's vtable contains a pointer to the supertrait's vtable:

```rust
trait Animal {
    fn name(&self) -> String;
}

trait Dog: Animal {
    fn bark(&self) -> String {
        format!("{}: woof!", self.name())
    }
}

struct Rex;
impl Animal for Rex { fn name(&self) -> String { "Rex".into() } }
impl Dog for Rex {}

fn main() {
    let d: &dyn Dog = &Rex;
    let a: &dyn Animal = d; // upcasting
    println!("{} / {}", d.bark(), a.name());
}
```

## The cost of monomorphization

Each instantiation `f::<T>` is a separate function in the binary. With many types and large generic functions, the binary and the compile time grow. Two techniques help:

- a thin generic shell over a non-generic inner function (see Functions, Expert level);
- `dyn Trait` on cold paths, where an indirect call doesn't matter.

`cargo llvm-lines` (an external crate) shows which generic functions take up the most LLVM code.

## Trait resolution

When you write `x.method()`, the compiler:

1. looks for the method on the type of `x`, then on `&x`, then on `&mut x`. If it doesn't find it, it applies `Deref` (`*x`) and repeats (*autoref / autoderef*);
2. at each step, it gathers the inherent methods (from `impl Type`) and those from the traits **in scope**. Inherent methods take priority;
3. if several candidates remain, it reports an ambiguity. You resolve it with fully qualified syntax:

```rust
trait Pilot { fn fly(&self) -> &'static str; }
trait Wizard { fn fly(&self) -> &'static str; }

struct Human;
impl Human { fn fly(&self) -> &'static str { "waves arms" } }
impl Pilot for Human { fn fly(&self) -> &'static str { "pilots" } }
impl Wizard for Human { fn fly(&self) -> &'static str { "levitates" } }

fn main() {
    let h = Human;
    println!("{}", h.fly());               // the inherent method takes priority
    println!("{}", Pilot::fly(&h));
    println!("{}", <Human as Wizard>::fly(&h)); // fully qualified
}
```

## Generic associated types (GAT)

Since Rust 1.65, an associated type can have its own generic parameters, including lifetimes. That lets you express a "lending iterator", which borrows from itself at each step. `Iterator` can't express this:

```rust
trait LendingIterator {
    type Item<'a> where Self: 'a;
    fn next(&mut self) -> Option<Self::Item<'_>>;
}

struct Windows {
    data: Vec<i32>,
    pos: usize,
}

impl LendingIterator for Windows {
    type Item<'a> = &'a mut [i32];

    fn next(&mut self) -> Option<&mut [i32]> {
        let start = self.pos;
        self.pos += 1;
        self.data.get_mut(start..start + 2)
    }
}

fn main() {
    let mut w = Windows { data: vec![1, 2, 3, 4], pos: 0 };
    while let Some(window) = w.next() {
        window[1] += window[0]; // modify through the borrowed window
        print!("{window:?} ");
    }
    println!();
}
```

## `PhantomData`: types without data

When a struct is generic over a type it doesn't actually store, `PhantomData<T>` tells the compiler how to behave: for variance, for drop check and for auto traits. A common example is units of measure checked at compile time:

```rust
use std::marker::PhantomData;
use std::ops::Add;

#[derive(Debug, Clone, Copy)]
struct Meters;
#[derive(Debug, Clone, Copy)]
struct Seconds;

#[derive(Debug, Clone, Copy)]
struct Quantity<U> {
    value: f64,
    _unit: PhantomData<U>, // zero-sized
}

impl<U> Quantity<U> {
    fn new(value: f64) -> Self { Quantity { value, _unit: PhantomData } }
}

impl<U> Add for Quantity<U> {
    type Output = Quantity<U>; // only quantities with the same unit add up
    fn add(self, other: Self) -> Self { Quantity::new(self.value + other.value) }
}

fn main() {
    let d = Quantity::<Meters>::new(100.0) + Quantity::new(50.0);
    let _t = Quantity::<Seconds>::new(9.58);
    // d + _t; // error: Quantity<Meters> + Quantity<Seconds> doesn't exist
    println!("{} m, {} bytes", d.value, size_of::<Quantity<Meters>>());
}
```

## Specialization (unstable)

It would be useful if a blanket implementation could be overridden for a particular type. The mechanism is called *specialization*, but it has been **unstable** for years, because the full version is unsound in the presence of lifetimes. The standard library internally uses a restricted version, `min_specialization`, for example so that `"text".to_string()` copies the bytes directly instead of going through `Display`.

> **Key takeaway:** `&dyn Trait` = data + vtable (drop, size, alignment, methods). Upcasting has been stable since 1.86. Methods are resolved through autoref/autoderef, with inherent methods first. GATs enable lending iterators, and `PhantomData` gives a generic semantics without data.
