# Traits și generics — Expert

Cum arată o vtable, ce costă monomorfizarea, ce sunt GAT-urile și cum rezolvă compilatorul ce implementare să folosească.

## Pointeri fat și vtable

Un `&dyn Trait` are **două** cuvinte: pointerul spre date și pointerul spre o vtable statică, generată pentru fiecare pereche (tip concret, trait). Vtable-ul conține, în ordine:

1. pointerul la `drop_in_place::<T>`;
2. mărimea lui `T`;
3. alinierea lui `T`;
4. pointerii la metodele trait-ului (și ale supertrait-urilor).

Layout-ul exact nu e garantat, dar aceste informații sunt accesibile prin API-uri sigure:

```rust
use std::fmt::Debug;
use std::mem::{align_of_val, size_of_val};

fn main() {
    let valori: [&dyn Debug; 3] = [&1u8, &[0u64; 4], &"text"];
    for v in valori {
        // mărimea și alinierea vin din vtable, la runtime
        println!("{v:?}: {} octeți, aliniere {}", size_of_val(v), align_of_val(v));
    }
    println!("&dyn Debug: {} octeți", size_of::<&dyn Debug>());
}
```

## Upcasting între obiecte trait

Din Rust 1.86, un `&dyn Sub` se poate converti direct în `&dyn Super` când `Super` e supertrait al lui `Sub`. Vtable-ul subtrait-ului conține un pointer către vtable-ul supertrait-ului:

```rust
trait Animal {
    fn nume(&self) -> String;
}

trait Caine: Animal {
    fn latra(&self) -> String {
        format!("{}: ham!", self.nume())
    }
}

struct Rex;
impl Animal for Rex { fn nume(&self) -> String { "Rex".into() } }
impl Caine for Rex {}

fn main() {
    let c: &dyn Caine = &Rex;
    let a: &dyn Animal = c; // upcasting
    println!("{} / {}", c.latra(), a.nume());
}
```

## Costul monomorfizării

Fiecare instanțiere `f::<T>` este o funcție separată în binar. Cu multe tipuri și funcții generice mari, binarul și timpul de compilare cresc. Două tehnici ajută:

- un strat generic subțire peste o funcție interioară non-generică (vezi Funcții, nivelul Expert);
- `dyn Trait` pe căile reci, unde un apel indirect nu contează.

`cargo llvm-lines` (crate extern) arată ce funcții generice ocupă cel mai mult cod LLVM.

## Rezolvarea trait-urilor

Când scrii `x.metoda()`, compilatorul:

1. caută metoda pe tipul lui `x`, apoi pe `&x`, apoi pe `&mut x`. Dacă nu o găsește, aplică `Deref` (`*x`) și reia (*autoref / autoderef*);
2. la fiecare pas, adună metodele inerente (din `impl Tip`) și pe cele din trait-urile **aflate în scope**. Metodele inerente au prioritate;
3. dacă rămân mai multe candidate, raportează ambiguitate. O rezolvi cu sintaxa complet calificată:

```rust
trait Pilot { fn zboara(&self) -> &'static str; }
trait Vrajitor { fn zboara(&self) -> &'static str; }

struct Om;
impl Om { fn zboara(&self) -> &'static str { "dă din mâini" } }
impl Pilot for Om { fn zboara(&self) -> &'static str { "pilotează" } }
impl Vrajitor for Om { fn zboara(&self) -> &'static str { "levitează" } }

fn main() {
    let om = Om;
    println!("{}", om.zboara());          // metoda inerentă are prioritate
    println!("{}", Pilot::zboara(&om));
    println!("{}", <Om as Vrajitor>::zboara(&om)); // complet calificat
}
```

## Tipuri asociate generice (GAT)

Din Rust 1.65, un tip asociat poate avea propriii parametri generici, inclusiv lifetimes. Așa poți exprima un „lending iterator”, care împrumută din el însuși la fiecare pas. `Iterator` nu poate exprima asta:

```rust
trait LendingIterator {
    type Item<'a> where Self: 'a;
    fn next(&mut self) -> Option<Self::Item<'_>>;
}

struct Ferestre {
    date: Vec<i32>,
    poz: usize,
}

impl LendingIterator for Ferestre {
    type Item<'a> = &'a mut [i32];

    fn next(&mut self) -> Option<&mut [i32]> {
        let start = self.poz;
        self.poz += 1;
        self.date.get_mut(start..start + 2)
    }
}

fn main() {
    let mut f = Ferestre { date: vec![1, 2, 3, 4], poz: 0 };
    while let Some(fereastra) = f.next() {
        fereastra[1] += fereastra[0]; // modificare prin fereastra împrumutată
        print!("{fereastra:?} ");
    }
    println!();
}
```

## `PhantomData`: tipuri fără date

Când un struct e generic peste un tip pe care nu îl stochează efectiv, `PhantomData<T>` spune compilatorului cum să se poarte: pentru variance, pentru drop check și pentru auto traits. Un exemplu frecvent sunt unitățile de măsură verificate la compilare:

```rust
use std::marker::PhantomData;
use std::ops::Add;

#[derive(Debug, Clone, Copy)]
struct Metri;
#[derive(Debug, Clone, Copy)]
struct Secunde;

#[derive(Debug, Clone, Copy)]
struct Marime<U> {
    valoare: f64,
    _unitate: PhantomData<U>, // mărime zero
}

impl<U> Marime<U> {
    fn new(valoare: f64) -> Self { Marime { valoare, _unitate: PhantomData } }
}

impl<U> Add for Marime<U> {
    type Output = Marime<U>; // se adună doar mărimi cu aceeași unitate
    fn add(self, alt: Self) -> Self { Marime::new(self.valoare + alt.valoare) }
}

fn main() {
    let d = Marime::<Metri>::new(100.0) + Marime::new(50.0);
    let _t = Marime::<Secunde>::new(9.58);
    // d + _t; // eroare: Marime<Metri> + Marime<Secunde> nu există
    println!("{} m, {} octeți", d.valoare, size_of::<Marime<Metri>>());
}
```

## Specializare (instabil)

Ar fi util ca o implementare blanket să poată fi suprascrisă pentru un tip anume. Mecanismul se numește *specialization*, dar e **instabil** de ani buni, pentru că varianta completă e nesigură în prezența lifetimes. Biblioteca standard folosește intern o versiune restrânsă, `min_specialization`, de exemplu ca `"text".to_string()` să copieze direct octeții în loc să treacă prin `Display`.

> **De reținut:** `&dyn Trait` = date + vtable (drop, mărime, aliniere, metode). Upcasting-ul e stabil din 1.86. Metodele se rezolvă prin autoref/autoderef, cu prioritate pentru cele inerente. GAT-urile permit lending iterators, iar `PhantomData` dă unui generic semantică fără date.
