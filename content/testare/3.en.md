# Testing — Advanced

How to make code testable, property-based testing, snapshots, benchmarks and asynchronous tests.

## Testable code: dependencies through traits

Code that reads the clock, the network or files directly is hard to test. If it receives its dependencies through a trait, in tests you can use a fake implementation:

```rust
pub trait Clock {
    fn hour(&self) -> u32;
}

pub struct SystemClock;
impl Clock for SystemClock {
    fn hour(&self) -> u32 {
        12 // in reality: the current hour from the system
    }
}

pub fn greeting(clock: &impl Clock) -> &'static str {
    match clock.hour() {
        5..=11 => "Good morning",
        12..=17 => "Good afternoon",
        _ => "Good evening",
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    struct FixedClock(u32);
    impl Clock for FixedClock {
        fn hour(&self) -> u32 { self.0 }
    }

    #[test]
    fn morning() {
        assert_eq!(greeting(&FixedClock(8)), "Good morning");
    }

    #[test]
    fn evening() {
        assert_eq!(greeting(&FixedClock(22)), "Good evening");
    }

    #[test]
    fn interval_boundaries() {
        for (hour, expected) in [(11, "Good morning"), (12, "Good afternoon"), (17, "Good afternoon"), (18, "Good evening")] {
            assert_eq!(greeting(&FixedClock(hour)), expected, "hour {hour}");
        }
    }
}
```

The `mockall` crate generates such fake implementations automatically, with expectations about the calls.

## Property-based testing

Instead of picking the examples yourself, you describe a **property** that must hold for any input. The library generates hundreds of random inputs. When it finds a counterexample, it **shrinks** it down to the simplest failing case:

```rust,ignore
// Cargo.toml: [dev-dependencies] proptest = "1"
use proptest::prelude::*;

fn reverse(s: &str) -> String {
    s.chars().rev().collect()
}

proptest! {
    #[test]
    fn reversing_twice_is_identity(s in ".*") {
        prop_assert_eq!(reverse(&reverse(&s)), s);
    }

    #[test]
    fn sorting_keeps_the_length(mut v in prop::collection::vec(any::<i32>(), 0..100)) {
        let n = v.len();
        v.sort();
        prop_assert_eq!(v.len(), n);
        prop_assert!(v.windows(2).all(|w| w[0] <= w[1]));
    }
}
```

Good properties to test: round trips (`decode(encode(x)) == x`), invariants (sorted, no duplicates), comparison with a simple, obviously correct implementation.

## Table-driven tests without libraries

For many similar cases, a list of input/expected pairs is simple and readable:

```rust
fn roman(mut n: u32) -> String {
    let table = [(1000, "M"), (900, "CM"), (500, "D"), (400, "CD"), (100, "C"), (90, "XC"),
                 (50, "L"), (40, "XL"), (10, "X"), (9, "IX"), (5, "V"), (4, "IV"), (1, "I")];
    let mut s = String::new();
    for (value, symbol) in table {
        while n >= value {
            s.push_str(symbol);
            n -= value;
        }
    }
    s
}

#[test]
fn roman_numerals() {
    let cases = [(1, "I"), (4, "IV"), (9, "IX"), (14, "XIV"), (1994, "MCMXCIV"), (2026, "MMXXVI")];
    for (n, expected) in cases {
        assert_eq!(roman(n), expected, "for {n}");
    }
}
```

## Snapshot testing

For large outputs (JSON, HTML, error messages), the `insta` crate saves the result to a file on the first run and compares against it on later runs. `cargo insta review` shows you the differences and lets you accept them.

## Asynchronous tests

With tokio, `#[tokio::test]` starts a runtime for each test:

```rust,ignore
#[tokio::test]
async fn responds_quickly() {
    let r = tokio::time::timeout(std::time::Duration::from_secs(1), async { 42 }).await;
    assert_eq!(r, Ok(42));
}
```

## Benchmarks

On stable, the standard is the **criterion** crate. It runs the function many times, analyzes the results statistically and reports changes against the previous run:

```rust,ignore
// benches/fib.rs   (Cargo.toml: [[bench]] name = "fib", harness = false)
use criterion::{criterion_group, criterion_main, Criterion};
use std::hint::black_box;

fn fib(n: u64) -> u64 {
    if n < 2 { n } else { fib(n - 1) + fib(n - 2) }
}

fn bench(c: &mut Criterion) {
    c.bench_function("fib 20", |b| b.iter(|| fib(black_box(20))));
}

criterion_group!(benches, bench);
criterion_main!(benches);
```

`black_box` prevents the optimizer from computing the result at compile time. Without it, you might be measuring a function that does nothing.

> **Key takeaway:** inject dependencies through traits so you can replace them in tests. `proptest` finds counterexamples on its own and shrinks them. Case tables are simple and clear. `#[tokio::test]` tests async code, and `criterion` measures performance correctly.
