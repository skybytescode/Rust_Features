# Testare — Expert

Cum funcționează harness-ul de teste, cum rulează în paralel, cum scrii unul propriu și ce unelte merg dincolo de testele obișnuite: Miri, fuzzing, coverage și testare prin mutații.

## Ce face `cargo test` de fapt

`cargo test` compilează crate-ul cu `rustc --test`. Flag-ul face trei lucruri:

1. activează `cfg(test)`, deci modulele `#[cfg(test)]` sunt incluse;
2. colectează toate funcțiile `#[test]` într-o listă statică;
3. generează o funcție `main` care pornește **libtest**, harness-ul standard, cu acea listă.

Fiecare fișier din `tests/`, fiecare exemplu din documentație și biblioteca însăși devin binare de test **separate**.

## Paralelism și izolare

Libtest rulează testele **în paralel**, pe thread-uri din același proces. Consecințe:

- testele care modifică stare globală (variabile de mediu, directorul curent, fișiere cu același nume) se pot influența reciproc;
- `cargo test -- --test-threads=1` le rulează secvențial, ca diagnostic, nu ca soluție;
- un test care dă panic e izolat pe thread-ul lui, dar un `abort` sau un `process::exit` oprește tot binarul.

Soluția corectă este izolarea: fiecare test cu propriul director temporar (crate-ul `tempfile`), fără variabile globale mutabile. Când chiar nu se poate, un `Mutex` static serializează testele care împart o resursă:

```rust
use std::sync::Mutex;

static RESURSA_PARTAJATA: Mutex<()> = Mutex::new(());

fn configureaza(valoare: &str) -> String {
    format!("config={valoare}")
}

#[test]
fn test_a() {
    let _g = RESURSA_PARTAJATA.lock().unwrap(); // doar unul odată
    assert_eq!(configureaza("a"), "config=a");
}

#[test]
fn test_b() {
    let _g = RESURSA_PARTAJATA.lock().unwrap();
    assert_eq!(configureaza("b"), "config=b");
}
```

Ediția 2024 a făcut `std::env::set_var` funcție `unsafe` tocmai pentru că modificarea mediului în timp ce alte thread-uri îl citesc e o cursă de date pe multe platforme.

## Harness propriu

Cu `harness = false` în `Cargo.toml`, binarul de test își scrie singur `main`. E util pentru teste generate din fișiere de date, pentru benchmark-uri (`criterion` lucrează așa) sau pentru framework-uri ca `libtest-mimic`:

```toml
[[test]]
name = "din_fisiere"
harness = false
```

```rust
// tests/din_fisiere.rs: un harness minimal
fn main() {
    let cazuri = [("2+2", 4), ("10-3", 7)];
    let mut esecuri = 0;
    for (intrare, asteptat) in cazuri {
        let rezultat = evalueaza(intrare);
        let ok = rezultat == asteptat;
        println!("{} {intrare} = {rezultat}", if ok { "ok  " } else { "FAIL" });
        if !ok {
            esecuri += 1;
        }
    }
    if esecuri > 0 {
        std::process::exit(1); // cod nenul: cargo raportează eșec
    }
}

fn evalueaza(s: &str) -> i32 {
    let (a, op, b) = s.find(['+', '-']).map(|i| (&s[..i], &s[i..i + 1], &s[i + 1..])).unwrap();
    let (a, b): (i32, i32) = (a.parse().unwrap(), b.parse().unwrap());
    if op == "+" { a + b } else { a - b }
}
```

## Miri pentru cod `unsafe`

Testele obișnuite nu detectează comportamentul nedefinit: un test cu UB poate trece. `cargo +nightly miri test` rulează aceleași teste în interpretorul Miri, care verifică aliasing-ul, alinierea, memoria neinițializată și cursele de date. Pentru biblioteci cu `unsafe`, e practic obligatoriu în CI.

## Fuzzing

Fuzzing-ul generează milioane de intrări, ghidat de **coverage**: păstrează intrările care ating cod nou. E excelent pentru parsere, decodoare și orice procesează date externe:

```bash
cargo install cargo-fuzz
cargo fuzz init
cargo +nightly fuzz run fuzz_target_1
```

```rust,ignore
// fuzz/fuzz_targets/fuzz_target_1.rs
#![no_main]
use libfuzzer_sys::fuzz_target;

fuzz_target!(|date: &[u8]| {
    if let Ok(text) = std::str::from_utf8(date) {
        let _ = parserul_meu::parseaza(text); // nu are voie să dea panic sau să producă UB
    }
});
```

## Coverage

```bash
cargo install cargo-llvm-cov
cargo llvm-cov --html     # raport HTML cu liniile acoperite
```

Intern se folosește `-C instrument-coverage`: LLVM inserează contoare în cod, iar raportul arată ce linii și ramuri au rulat. Coverage mare nu înseamnă teste bune, dar coverage mic arată sigur codul netestat.

## Testare prin mutații

`cargo-mutants` modifică automat codul (de exemplu, înlocuiește `<` cu `<=`, returnează `Default::default()` sau șterge un apel) și rulează testele. Dacă testele trec și după mutație, înseamnă că nu verifică acel comportament. Unealta răspunde la întrebarea pe care coverage-ul n-o poate pune: „ar observa testele mele dacă acest cod ar fi greșit?”.

## `cargo nextest`

`cargo-nextest` rulează fiecare test într-un **proces separat**: izolare completă, retry pentru testele instabile, output mai clar și, adesea, execuție mai rapidă pe mașini cu multe nuclee. Nu rulează însă testele din documentație, pentru care rămâne nevoie de `cargo test --doc`.

> **De reținut:** `rustc --test` generează un `main` care pornește libtest. Testele rulează în paralel, în același proces, deci izolează starea globală. `harness = false` îți dă control complet. Miri, fuzzing-ul, coverage-ul și testarea prin mutații acoperă ce testele obișnuite nu pot.
