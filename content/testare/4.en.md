# Testing — Expert

How the test harness works, how tests run in parallel, how to write your own harness, and which tools go beyond ordinary tests: Miri, fuzzing, coverage and mutation testing.

## What `cargo test` really does

`cargo test` compiles the crate with `rustc --test`. The flag does three things:

1. enables `cfg(test)`, so the `#[cfg(test)]` modules are included;
2. collects all `#[test]` functions into a static list;
3. generates a `main` function that starts **libtest**, the standard harness, with that list.

Each file in `tests/`, each documentation example and the library itself become **separate** test binaries.

## Parallelism and isolation

Libtest runs tests **in parallel**, on threads in the same process. Consequences:

- tests that modify global state (environment variables, the current directory, files with the same name) can affect each other;
- `cargo test -- --test-threads=1` runs them sequentially, as a diagnostic, not as a fix;
- a test that panics is isolated on its own thread, but an `abort` or a `process::exit` stops the whole binary.

The correct fix is isolation: each test with its own temporary directory (the `tempfile` crate), with no mutable global variables. When it really isn't possible, a static `Mutex` serializes the tests that share a resource:

```rust
use std::sync::Mutex;

static SHARED_RESOURCE: Mutex<()> = Mutex::new(());

fn configure(value: &str) -> String {
    format!("config={value}")
}

#[test]
fn test_a() {
    let _g = SHARED_RESOURCE.lock().unwrap(); // only one at a time
    assert_eq!(configure("a"), "config=a");
}

#[test]
fn test_b() {
    let _g = SHARED_RESOURCE.lock().unwrap();
    assert_eq!(configure("b"), "config=b");
}
```

The 2024 edition made `std::env::set_var` an `unsafe` function precisely because modifying the environment while other threads read it is a data race on many platforms.

## Your own harness

With `harness = false` in `Cargo.toml`, the test binary writes its own `main`. That's useful for tests generated from data files, for benchmarks (`criterion` works this way) or for frameworks such as `libtest-mimic`:

```toml
[[test]]
name = "from_files"
harness = false
```

```rust
// tests/from_files.rs: a minimal harness
fn main() {
    let cases = [("2+2", 4), ("10-3", 7)];
    let mut failures = 0;
    for (input, expected) in cases {
        let result = evaluate(input);
        let ok = result == expected;
        println!("{} {input} = {result}", if ok { "ok  " } else { "FAIL" });
        if !ok {
            failures += 1;
        }
    }
    if failures > 0 {
        std::process::exit(1); // non-zero code: cargo reports a failure
    }
}

fn evaluate(s: &str) -> i32 {
    let (a, op, b) = s.find(['+', '-']).map(|i| (&s[..i], &s[i..i + 1], &s[i + 1..])).unwrap();
    let (a, b): (i32, i32) = (a.parse().unwrap(), b.parse().unwrap());
    if op == "+" { a + b } else { a - b }
}
```

## Miri for `unsafe` code

Ordinary tests don't detect undefined behavior: a test with UB can pass. `cargo +nightly miri test` runs the same tests in the Miri interpreter, which checks aliasing, alignment, uninitialized memory and data races. For libraries with `unsafe`, it's practically mandatory in CI.

## Fuzzing

Fuzzing generates millions of inputs, guided by **coverage**: it keeps the inputs that reach new code. It's excellent for parsers, decoders and anything that processes external data:

```bash
cargo install cargo-fuzz
cargo fuzz init
cargo +nightly fuzz run fuzz_target_1
```

```rust,ignore
// fuzz/fuzz_targets/fuzz_target_1.rs
#![no_main]
use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    if let Ok(text) = std::str::from_utf8(data) {
        let _ = my_parser::parse(text); // must not panic or cause UB
    }
});
```

## Coverage

```bash
cargo install cargo-llvm-cov
cargo llvm-cov --html     # HTML report with the covered lines
```

Internally it uses `-C instrument-coverage`: LLVM inserts counters into the code, and the report shows which lines and branches ran. High coverage doesn't mean good tests, but low coverage reliably shows untested code.

## Mutation testing

`cargo-mutants` automatically modifies the code (for example, replaces `<` with `<=`, returns `Default::default()` or deletes a call) and runs the tests. If the tests still pass after the mutation, they don't check that behavior. The tool answers the question coverage can't ask: "would my tests notice if this code were wrong?".

## `cargo nextest`

`cargo-nextest` runs each test in a **separate process**: full isolation, retries for flaky tests, clearer output and often faster execution on machines with many cores. It doesn't run documentation tests, though, so you still need `cargo test --doc` for those.

> **Key takeaway:** `rustc --test` generates a `main` that starts libtest. Tests run in parallel, in the same process, so isolate global state. `harness = false` gives you full control. Miri, fuzzing, coverage and mutation testing cover what ordinary tests can't.
