# Lifetimes — Expert

Ce sunt lifetimes pentru compilator: regiuni în MIR, constrângeri rezolvate de borrow checker, plus drop check și relația cu `PhantomData`.

## Lifetimes sunt regiuni în graful de control

În MIR, fiecare referință primește o **regiune**: mulțimea punctelor din graful de control în care referința trebuie să fie validă. Borrow checker-ul (NLL):

1. adună **constrângeri** de forma `'a: 'b` („regiunea `'a` include regiunea `'b`”) din atribuiri, apeluri și semnături;
2. calculează cea mai mică soluție, adică regiunile minime care le respectă pe toate;
3. pentru fiecare împrumut activ într-un punct, verifică să nu existe o acțiune conflictuală: o scriere peste un împrumut partajat, un move, un drop sau un al doilea `&mut`.

Lifetimes din semnături sunt **parametri universali**. Funcția trebuie să fie corectă pentru orice valoare a lor, de aceea în corpul funcției nu poți „alege” un `'a` convenabil.

## Lifetimes nu există la runtime

După verificare, lifetimes sunt șterse complet: nu influențează codul generat și nici layout-ul. O consecință: nu poți face dispatch pe lifetime. Nici specializarea nu poate depinde de el, și acesta e unul dintre motivele pentru care specializarea completă nu e sigură.

## Drop check

Când o valoare are un `Drop` propriu, destructorul ei **ar putea** citi referințele pe care le conține. Compilatorul cere atunci ca datele împrumutate să fie încă vii în momentul drop-ului:

```rust,compile_fail
struct Logger<'a> {
    nume: &'a String,
}

impl Drop for Logger<'_> {
    fn drop(&mut self) {
        println!("închid {}", self.nume); // citește referința în drop
    }
}

fn main() {
    let logger;
    let nume = String::from("app"); // declarat după `logger`, deci distrus înaintea lui
    logger = Logger { nume: &nume };
    // eroare E0597: `nume` e distrus înainte ca Drop-ul lui `logger` să-l citească
}
```

Fără `impl Drop`, exemplul compilează. Compilatorul știe că un drop „trivial” nu atinge referința. Același mecanism decide pentru tipurile generice: `Vec<&'a T>` poate fi distrus după `T`, pentru că biblioteca standard folosește atributul instabil `#[may_dangle]` și promite că destructorul lui `Vec` nu citește valorile `T` decât prin propriul lor drop.

## `PhantomData` și variance

Într-un tip scris cu pointeri bruți (`*const T`, `NonNull<T>`), compilatorul nu știe ce relație are tipul cu `T` sau cu un lifetime. `PhantomData` o declară explicit:

| Câmp | Efect |
|---|---|
| `PhantomData<T>` | „dețin un `T`”: covariant, contează la drop check |
| `PhantomData<&'a T>` | „împrumut un `T` pentru `'a`”: covariant în `'a` și în `T` |
| `PhantomData<&'a mut T>` | invariant în `T` |
| `PhantomData<fn(T)>` | contravariant în `T` |
| `PhantomData<*mut T>` | invariant și **nu** e `Send` / `Sync` |

```rust
use std::marker::PhantomData;

// O vedere peste un slice, construită cu pointer brut
struct Vedere<'a, T> {
    ptr: *const T,
    len: usize,
    _imprumut: PhantomData<&'a [T]>, // leagă Vedere de lifetime-ul slice-ului
}

impl<'a, T> Vedere<'a, T> {
    fn new(s: &'a [T]) -> Self {
        Vedere { ptr: s.as_ptr(), len: s.len(), _imprumut: PhantomData }
    }

    fn primul(&self) -> Option<&'a T> {
        // SAFETY: ptr și len provin dintr-un slice valid pentru 'a
        (self.len > 0).then(|| unsafe { &*self.ptr })
    }
}

fn main() {
    let date = vec![10, 20];
    let v = Vedere::new(&date);
    println!("{:?}", v.primul());
    // drop(date); // eroare: `date` e încă împrumutat de `v` datorită PhantomData
    println!("{:?}", v.primul());
}
```

Fără câmpul `PhantomData`, structura nu ar folosi deloc `'a`, iar compilatorul ar respinge definiția (E0392). Cu un lifetime ales greșit, ai obține o vedere care supraviețuiește datelor.

## Polonius

**Polonius** este următoarea generație a borrow checker-ului. Nu mai întreabă „în ce puncte trebuie să fie vie regiunea?”, ci „din ce împrumuturi (*loans*) poate proveni această referință?”. Acceptă programe corecte pe care NLL le respinge. Cel mai cunoscut caz e returnarea condiționată a unui împrumut:

```rust,compile_fail
use std::collections::HashMap;

fn obtine_sau_insereaza(m: &mut HashMap<u32, String>) -> &String {
    if let Some(v) = m.get(&1) {
        return v; // NLL: împrumutul lui `m` e considerat activ până la finalul funcției
    }
    m.insert(1, "nou".into()); // eroare E0502 cu NLL, acceptat de Polonius
    &m[&1]
}

fn main() {
    let mut m = HashMap::new();
    println!("{}", obtine_sau_insereaza(&mut m));
}
```

Până la stabilizarea lui Polonius, soluția este entry API-ul (`m.entry(1).or_insert_with(...)`) sau o a doua căutare. Pe nightly poți încerca algoritmul cu `-Z polonius`.

> **De reținut:** lifetimes sunt regiuni în MIR, deduse ca soluție minimă a unor constrângeri și șterse după verificare. Drop check-ul cere date vii doar când există un `Drop` care le-ar putea citi. `PhantomData` stabilește variance pentru tipurile cu pointeri bruți, iar Polonius va accepta împrumuturile returnate condiționat.
