# Lifetimes — Practitioner

The rules by which the compiler infers lifetimes, structs that hold references, and how to read common errors.

## The elision rules

When you don't write lifetimes in a function signature, the compiler applies three rules:

1. Each reference in the parameters gets its own lifetime.
2. If there is **exactly one** input lifetime, it applies to every returned reference.
3. If one of the parameters is `&self` or `&mut self`, its lifetime applies to the returned references.

If after these rules the result still has no lifetime, you have to write it yourself.

```rust
struct Document {
    title: String,
    body: String,
}

impl Document {
    // rule 3: the result lives as long as `self`
    fn title(&self) -> &str {
        &self.title
    }

    // still rule 3, even though there is another reference parameter
    fn search(&self, _word: &str) -> &str {
        &self.body
    }
}

fn main() {
    let d = Document { title: "Report".into(), body: "...".into() };
    println!("{} {}", d.title(), d.search("x"));
}
```

## Structs that hold references

A struct containing a reference needs a lifetime parameter. The instance can't outlive the borrowed data:

```rust
struct Parser<'a> {
    text: &'a str,
    pos: usize,
}

impl<'a> Parser<'a> {
    fn new(text: &'a str) -> Self {
        Parser { text, pos: 0 }
    }

    // returns a piece of the original text, not of the parser
    fn next_word(&mut self) -> Option<&'a str> {
        let rest = self.text[self.pos..].trim_start();
        if rest.is_empty() {
            return None;
        }
        let start = self.text.len() - rest.len();
        let end = rest.find(' ').map_or(self.text.len(), |i| start + i);
        self.pos = end;
        Some(&self.text[start..end])
    }
}

fn main() {
    let text = String::from("one two three");
    let mut p = Parser::new(&text);
    let mut words = Vec::new();
    while let Some(w) = p.next_word() {
        words.push(w);
    }
    drop(p); // the words stay valid: they belong to `text`, not to the parser
    println!("{words:?}");
}
```

The explicit lifetime `'a` in the return type matters: with a plain `&str`, rule 3 would tie the words to `&mut self`, and while you held a word you couldn't call the parser again.

## References or owned data?

Structs with references suit **short-lived** objects: parsers, iterators, views over data. For objects that live long or travel from one part of the program to another, use owned data (`String`, `Vec`). The code becomes much simpler, and a copy usually costs less than you think.

## Common errors

**"borrowed value does not live long enough" (E0597).** The borrowed value is destroyed before the last use of the reference. Move the value's declaration higher up or return owned data.

**"missing lifetime specifier" (E0106).** A function returns a reference, and the elision rules can't decide where it comes from. Add `<'a>` and tie the result to the right parameter.

**"lifetime may not live long enough".** You promised a relationship in the signature that the code doesn't respect:

```rust,compile_fail
fn choose<'a, 'b>(x: &'a str, y: &'b str) -> &'a str {
    if x.is_empty() { y } else { x } // error: `y` has lifetime 'b, not 'a
}

fn main() {
    println!("{}", choose("", "b"));
}
```

## `'static` as a constraint

`T: 'static` does **not** mean "T lives for the entire program". It means "T contains no references that could expire". A `String` satisfies `'static`, even though it's created at runtime and can be destroyed at any time. That's why `thread::spawn` requires `'static`:

```rust
fn main() {
    let message = String::from("from another thread");
    let h = std::thread::spawn(move || {
        println!("{message}"); // String: 'static, because it is moved, not borrowed
    });
    h.join().unwrap();
}
```

> **Key takeaway:** three elision rules cover most functions. A struct with references needs `<'a>` and can't outlive its data. `T: 'static` means "no temporary references", not "lives forever".
