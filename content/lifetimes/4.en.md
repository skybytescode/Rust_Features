# Lifetimes — Expert

What lifetimes are to the compiler: regions in MIR, constraints solved by the borrow checker, plus drop check and the relationship with `PhantomData`.

## Lifetimes are regions in the control-flow graph

In MIR, each reference gets a **region**: the set of points in the control-flow graph where the reference must be valid. The borrow checker (NLL):

1. gathers **constraints** of the form `'a: 'b` ("region `'a` includes region `'b`") from assignments, calls and signatures;
2. computes the smallest solution, that is the minimal regions that satisfy all of them;
3. for each borrow active at a point, checks that there is no conflicting action: a write over a shared borrow, a move, a drop or a second `&mut`.

Lifetimes in signatures are **universal parameters**. The function must be correct for any value they take, which is why inside the function body you can't "pick" a convenient `'a`.

## Lifetimes don't exist at runtime

After the check, lifetimes are erased completely: they don't influence the generated code or the layout. One consequence: you can't dispatch on a lifetime. Specialization can't depend on it either, and that's one of the reasons full specialization isn't sound.

## Drop check

When a value has its own `Drop`, its destructor **might** read the references it contains. The compiler then requires the borrowed data to still be alive at the moment of the drop:

```rust,compile_fail
struct Logger<'a> {
    name: &'a String,
}

impl Drop for Logger<'_> {
    fn drop(&mut self) {
        println!("closing {}", self.name); // reads the reference in drop
    }
}

fn main() {
    let logger;
    let name = String::from("app"); // declared after `logger`, so destroyed before it
    logger = Logger { name: &name };
    // error E0597: `name` is destroyed before `logger`'s Drop reads it
}
```

Without `impl Drop`, the example compiles. The compiler knows a "trivial" drop doesn't touch the reference. The same mechanism decides for generic types: a `Vec<&'a T>` can be destroyed after `T`, because the standard library uses the unstable `#[may_dangle]` attribute and promises that `Vec`'s destructor doesn't read the `T` values except through their own drop.

## `PhantomData` and variance

In a type written with raw pointers (`*const T`, `NonNull<T>`), the compiler doesn't know how the type relates to `T` or to a lifetime. `PhantomData` declares it explicitly:

| Field | Effect |
|---|---|
| `PhantomData<T>` | "I own a `T`": covariant, counts for drop check |
| `PhantomData<&'a T>` | "I borrow a `T` for `'a`": covariant in `'a` and in `T` |
| `PhantomData<&'a mut T>` | invariant in `T` |
| `PhantomData<fn(T)>` | contravariant in `T` |
| `PhantomData<*mut T>` | invariant and **not** `Send` / `Sync` |

```rust
use std::marker::PhantomData;

// A view over a slice, built with a raw pointer
struct View<'a, T> {
    ptr: *const T,
    len: usize,
    _borrow: PhantomData<&'a [T]>, // ties View to the slice's lifetime
}

impl<'a, T> View<'a, T> {
    fn new(s: &'a [T]) -> Self {
        View { ptr: s.as_ptr(), len: s.len(), _borrow: PhantomData }
    }

    fn first(&self) -> Option<&'a T> {
        // SAFETY: ptr and len come from a slice that is valid for 'a
        (self.len > 0).then(|| unsafe { &*self.ptr })
    }
}

fn main() {
    let data = vec![10, 20];
    let v = View::new(&data);
    println!("{:?}", v.first());
    // drop(data); // error: `data` is still borrowed by `v`, thanks to PhantomData
    println!("{:?}", v.first());
}
```

Without the `PhantomData` field, the struct wouldn't use `'a` at all, and the compiler would reject the definition (E0392). With a wrongly chosen lifetime, you'd get a view that outlives its data.

## Polonius

**Polonius** is the next generation of the borrow checker. Instead of asking "at which points must the region be alive?", it asks "which borrows (*loans*) can this reference come from?". It accepts correct programs that NLL rejects. The best-known case is conditionally returning a borrow:

```rust,compile_fail
use std::collections::HashMap;

fn get_or_insert(m: &mut HashMap<u32, String>) -> &String {
    if let Some(v) = m.get(&1) {
        return v; // NLL: the borrow of `m` is considered active until the end of the function
    }
    m.insert(1, "new".into()); // error E0502 with NLL, accepted by Polonius
    &m[&1]
}

fn main() {
    let mut m = HashMap::new();
    println!("{}", get_or_insert(&mut m));
}
```

Until Polonius is stabilized, the solution is the entry API (`m.entry(1).or_insert_with(...)`) or a second lookup. On nightly you can try the algorithm with `-Z polonius`.

> **Key takeaway:** lifetimes are regions in MIR, inferred as the minimal solution to a set of constraints and erased after the check. Drop check requires live data only when there's a `Drop` that might read it. `PhantomData` sets variance for types with raw pointers, and Polonius will accept conditionally returned borrows.
