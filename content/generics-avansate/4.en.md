# Advanced generics — Expert

How the compiler resolves overlapping implementations, what "fundamental" types mean, how const generics combine with compile-time evaluation, and how you can compute at the type level.

## Coherence: why some implementations reject each other

The compiler guarantees that for any (trait, type) pair there is **at most one** implementation. Two blanket implementations can overlap even hypothetically, and that's enough for them to be rejected:

```rust,compile_fail
use std::fmt::{Debug, Display};

trait Describe {
    fn describe(&self) -> String;
}

impl<T: Display> Describe for T {
    fn describe(&self) -> String { format!("{self}") }
}

impl<T: Debug> Describe for T { // error E0119: a type can have both Display and Debug
    fn describe(&self) -> String { format!("{self:?}") }
}

fn main() {}
```

Without *specialization* (unstable), the solutions are a newtype (`struct AsDebug<T>(T)`) or concrete implementations, type by type.

The compiler also reasons about the **future**: an implementation is rejected if an upstream crate could add, without a breaking change, an implementation that would conflict with it.

Coherence is also the source of a restriction that often surprises people: you can't implement a foreign trait for a "bare" generic parameter. For example, a conversion back from your type into some arbitrary `T`. `T` could be any foreign type, and the orphan rule requires the type you implement for to be covered by a local type:

```rust,compile_fail
struct Boxed<T>(T);

impl<T> From<Boxed<T>> for T { // error E0210: T is an unknown foreign type
    fn from(b: Boxed<T>) -> T { b.0 }
}

fn main() {}
```

## Fundamental types

The orphan rule has a controlled exception: the types internally marked `#[fundamental]`, namely `&T`, `&mut T`, `Box<T>` and `Pin<P>`. For coherence, `Box<MyType>` counts as a **local** type, so you can write `impl ForeignTrait for Box<MyType>`. In exchange, the standard library can't add new blanket implementations for `Box<T>` without a breaking change.

## Monomorphization of const generics

Each distinct value of a `const` parameter produces a separate instance, just like a distinct type. `sum::<3>` and `sum::<8>` are two functions in the binary. For large arrays used with many sizes, an inner function on slices reduces the generated code:

```rust
fn sum<const N: usize>(a: [u64; N]) -> u64 {
    fn inner(s: &[u64]) -> u64 { s.iter().sum() } // compiled only once
    inner(&a)
}

fn main() {
    println!("{} {}", sum([1; 3]), sum([2; 100]));
}
```

## Compile-time checks with `const` blocks

A `const` item or block inside a generic context is evaluated **at monomorphization**, for each instance. An `assert!` there becomes a compile error only for the invalid instances:

```rust
struct Aligned<const N: usize>;

impl<const N: usize> Aligned<N> {
    const VALID: () = assert!(N.is_power_of_two(), "N must be a power of 2");

    fn new() -> Self {
        let () = Self::VALID; // forces the evaluation for this N
        Aligned
    }
}

fn main() {
    let _a = Aligned::<64>::new();
    // let _b = Aligned::<48>::new(); // compile error: N must be a power of 2
    println!("ok");
}
```

The technique replaces runtime checks with static guarantees, even though generic expressions aren't yet allowed in types.

## Historical limits: arrays and traits

Before const generics (Rust 1.51), traits for arrays were implemented with macros, only up to 32 elements. Most of those limits are gone, but a few remain for compatibility reasons. `Default` is implemented only for `[T; 0]`…`[T; 32]`, because `[T; 0]` doesn't require `T: Default`, and a generic implementation would change that behavior:

```rust
fn main() {
    let a: [u8; 32] = Default::default();             // OK
    // let b: [u8; 33] = Default::default();          // error: [u8; 33] doesn't implement Default
    let b: [u8; 33] = [0; 33];                        // the alternative
    let c: [String; 40] = std::array::from_fn(|_| String::new()); // for non-Copy types
    println!("{} {} {}", a.len(), b.len(), c.len());
}
```

## Type-level programming

Types can encode information checked at compile time, with no runtime cost at all. An example: Peano-style natural numbers, used as statically checked lengths:

```rust
use std::marker::PhantomData;

struct Zero;
struct Succ<N>(PhantomData<N>);

trait Natural {
    const VALUE: usize;
}
impl Natural for Zero {
    const VALUE: usize = 0;
}
impl<N: Natural> Natural for Succ<N> {
    const VALUE: usize = N::VALUE + 1;
}

type Three = Succ<Succ<Succ<Zero>>>;

fn main() {
    println!("{}", <Three as Natural>::VALUE);
    println!("{} bytes", size_of::<Three>()); // 0: everything exists only at compile time
}
```

The `typenum` crate takes the idea further, with type-level arithmetic. Most practical cases have moved to const generics, though.

> **Key takeaway:** coherence rejects any possible overlap, including a future one. `&T`, `Box<T>` and `Pin` are fundamental for the orphan rule. Each const value produces a separate instance. `const` items with `assert!` give per-instance checks at compile time.
