# Generics avansate — Expert

Cum rezolvă compilatorul suprapunerea implementărilor, ce înseamnă tipurile „fundamentale”, cum se combină const generics cu evaluarea la compilare și cum poți face calcule la nivel de tip.

## Coerența: de ce unele implementări se resping între ele

Compilatorul garantează că pentru orice pereche (trait, tip) există **cel mult o** implementare. Două implementări blanket se pot suprapune chiar și ipotetic, iar asta e de ajuns ca să fie respinse:

```rust,compile_fail
use std::fmt::{Debug, Display};

trait Descrie {
    fn descrie(&self) -> String;
}

impl<T: Display> Descrie for T {
    fn descrie(&self) -> String { format!("{self}") }
}

impl<T: Debug> Descrie for T { // eroare E0119: un tip poate avea și Display, și Debug
    fn descrie(&self) -> String { format!("{self:?}") }
}

fn main() {}
```

Fără *specialization* (instabilă), soluțiile sunt un newtype (`struct CaDebug<T>(T)`) sau implementări concrete, tip cu tip.

Compilatorul raționează și despre **viitor**: o implementare e respinsă dacă un crate din amonte ar putea adăuga, fără breaking change, o implementare care ar intra în conflict cu ea.

Tot din coerență vine o restricție care surprinde des: nu poți implementa un trait străin pentru un parametru generic „gol”. De exemplu, o conversie înapoi din tipul tău într-un `T` oarecare. `T` ar putea fi orice tip străin, iar regula orfanului cere ca tipul pentru care implementezi să fie acoperit de un tip local:

```rust,compile_fail
struct Cutie<T>(T);

impl<T> From<Cutie<T>> for T { // eroare E0210: T e un tip străin necunoscut
    fn from(c: Cutie<T>) -> T { c.0 }
}

fn main() {}
```

## Tipuri fundamentale

Regula orfanului are o excepție controlată: tipurile marcate intern cu `#[fundamental]`, adică `&T`, `&mut T`, `Box<T>` și `Pin<P>`. Pentru coerență, `Box<TipulMeu>` contează ca un tip **local**, așa că poți scrie `impl TraitStrain for Box<TipulMeu>`. În schimb, biblioteca standard nu poate adăuga, fără breaking change, implementări noi blanket pentru `Box<T>`.

## Monomorfizarea const generics

Fiecare valoare distinctă a unui parametru `const` produce o instanță separată, la fel ca un tip distinct. `suma::<3>` și `suma::<8>` sunt două funcții în binar. Pentru array-uri mari folosite cu multe dimensiuni, o funcție interioară pe slice-uri reduce codul generat:

```rust
fn suma<const N: usize>(a: [u64; N]) -> u64 {
    fn interior(s: &[u64]) -> u64 { s.iter().sum() } // compilată o singură dată
    interior(&a)
}

fn main() {
    println!("{} {}", suma([1; 3]), suma([2; 100]));
}
```

## Verificări la compilare cu `const` blocks

Un bloc `const { ... }` dintr-o funcție generică e evaluat **la monomorfizare**, pentru fiecare instanță. Un `assert!` acolo devine o eroare de compilare doar pentru instanțele invalide:

```rust
struct Aliniat<const N: usize>;

impl<const N: usize> Aliniat<N> {
    const VALID: () = assert!(N.is_power_of_two(), "N trebuie să fie putere a lui 2");

    fn new() -> Self {
        let () = Self::VALID; // forțează evaluarea pentru acest N
        Aliniat
    }
}

fn main() {
    let _a = Aliniat::<64>::new();
    // let _b = Aliniat::<48>::new(); // eroare la compilare: N trebuie să fie putere a lui 2
    println!("ok");
}
```

Tehnica înlocuiește verificările de la runtime cu garanții statice, chiar dacă expresiile generice nu sunt încă permise în tipuri.

## Limite istorice: array-uri și trait-uri

Înainte de const generics (Rust 1.51), trait-urile pentru array-uri erau implementate cu macro-uri, doar până la 32 de elemente. Majoritatea limitelor au dispărut, dar câteva au rămas din motive de compatibilitate. `Default` e implementat doar pentru `[T; 0]`…`[T; 32]`, pentru că `[T; 0]` nu cere `T: Default`, iar o implementare generică ar schimba acest comportament:

```rust
fn main() {
    let a: [u8; 32] = Default::default();             // OK
    // let b: [u8; 33] = Default::default();          // eroare: [u8; 33] nu implementează Default
    let b: [u8; 33] = [0; 33];                        // alternativa
    let c: [String; 40] = std::array::from_fn(|_| String::new()); // pentru tipuri non-Copy
    println!("{} {} {}", a.len(), b.len(), c.len());
}
```

## Programare la nivel de tip

Tipurile pot codifica informații verificate la compilare, fără niciun cost la runtime. Un exemplu: numere naturale de tip Peano, folosite ca lungimi verificate static:

```rust
use std::marker::PhantomData;

struct Zero;
struct Succ<N>(PhantomData<N>);

trait Natural {
    const VALOARE: usize;
}
impl Natural for Zero {
    const VALOARE: usize = 0;
}
impl<N: Natural> Natural for Succ<N> {
    const VALOARE: usize = N::VALOARE + 1;
}

type Trei = Succ<Succ<Succ<Zero>>>;

fn main() {
    println!("{}", <Trei as Natural>::VALOARE);
    println!("{} octeți", size_of::<Trei>()); // 0: totul există doar la compilare
}
```

Crate-ul `typenum` duce ideea mai departe, cu aritmetică la nivel de tip. Majoritatea cazurilor practice s-au mutat însă pe const generics.

> **De reținut:** coerența respinge orice suprapunere posibilă, inclusiv una viitoare. `&T`, `Box<T>` și `Pin` sunt fundamentale pentru regula orfanului. Fiecare valoare const produce o instanță separată. Blocurile `const` cu `assert!` dau verificări per instanță, la compilare.
