# Unsafe and FFI — Fundamentals

The Rust compiler checks memory strictly, but some correct operations can't be proven safe automatically. For those there's `unsafe`: a block in which **you** guarantee correctness, not the compiler.

## What `unsafe` means

`unsafe` does **not** turn off the checks. The borrow checker, types and ownership keep working. `unsafe` only unlocks five extra operations:

1. dereferencing a **raw pointer** (`*const T`, `*mut T`);
2. calling an `unsafe` function, including functions from other languages;
3. reading or modifying a `static mut` variable;
4. implementing an `unsafe` trait;
5. reading the fields of a `union`.

## Raw pointers

A raw pointer is like a C pointer: it can be null, it can point to freed memory and it isn't checked by the borrow checker. You can **create** one anytime, but you can **use** it only in `unsafe`:

```rust
fn main() {
    let mut x = 10;
    let p = &mut x as *mut i32; // creating it is safe

    unsafe {
        // SAFETY: `p` comes from a valid reference to `x`, which is still alive
        *p += 5;
        println!("x = {}", *p);
    }
}
```

The `// SAFETY:` comment explains **why** the operation is correct. It's a strong convention in the Rust community.

## Without `unsafe`, the compiler refuses

```rust,compile_fail
fn main() {
    let x = 5;
    let p = &x as *const i32;
    println!("{}", *p); // error E0133: dereferencing requires `unsafe`
}
```

## `unsafe` functions

A function marked `unsafe fn` has **conditions** the caller must uphold. The standard library has a few, for example `get_unchecked`, which skips the index check:

```rust
fn main() {
    let v = vec![10, 20, 30];
    let i = 1;
    if i < v.len() {
        // SAFETY: we checked above that `i` is in bounds
        let x = unsafe { *v.get_unchecked(i) };
        println!("{x}");
    }
}
```

## FFI: calling C code

**FFI** (*Foreign Function Interface*) lets you call functions written in C or another language. You declare them in an `extern "C"` block:

```rust
unsafe extern "C" {
    fn abs(x: i32) -> i32; // a function from the C standard library
}

fn main() {
    // SAFETY: libc's `abs` accepts any i32 (except i32::MIN, which we don't pass)
    let r = unsafe { abs(-42) };
    println!("{r}");
}
```

The compiler can't check what the C code does, so the call is `unsafe`.

## When to use `unsafe`

Rarely. In almost any application, your code doesn't need `unsafe`. It shows up in:

- low-level libraries (data structures, allocators, drivers);
- bindings to C libraries;
- extreme optimizations, after you've measured that they are necessary.

> **Key takeaway:** `unsafe` unlocks five extra operations; it doesn't turn off the checks. Raw pointers can be created freely, but used only in `unsafe`. Always write a `// SAFETY:` comment. FFI goes through `extern "C"` blocks.
