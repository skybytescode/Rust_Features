# Unsafe și FFI — Avansat

Ce este concret comportamentul nedefinit, cum folosești corect pointerii bruți, de ce `transmute` e periculos și cum treci callbacks între Rust și C.

## Comportament nedefinit (UB)

Codul `unsafe` corect nu are voie să producă **niciodată** comportament nedefinit. Câteva surse frecvente:

- dereferențierea unui pointer nul, nealiniat sau către memorie eliberată;
- încălcarea regulilor de aliasing: două `&mut` active către aceeași memorie, sau modificare prin `&T` fără `UnsafeCell`;
- o valoare invalidă pentru tipul ei: un `bool` cu valoarea 2, un `char` invalid, o referință nulă, o valoare de enum inexistentă;
- citirea memoriei neinițializate (cu excepția `MaybeUninit`);
- o cursă de date;
- un panic care traversează o graniță `extern "C"`.

UB nu înseamnă „probabil se blochează”. Înseamnă că **compilatorul presupune că nu se întâmplă niciodată** și optimizează pe baza acestei presupuneri. Un program cu UB poate funcționa perfect în debug și greșit în release.

## Aritmetica pe pointeri

```rust
fn main() {
    let v = [10u32, 20, 30, 40];
    let p = v.as_ptr();

    // SAFETY: indicii 0..4 sunt în interiorul array-ului
    unsafe {
        for i in 0..v.len() {
            print!("{} ", *p.add(i)); // `add` folosește unități de element, nu octeți
        }
    }
    println!();

    let capat = p.wrapping_add(v.len()); // un pointer „după ultimul element” e permis
    // SAFETY: ambii pointeri provin din același array
    println!("distanța: {}", unsafe { capat.offset_from(p) });
}
```

`add` / `offset` cer ca rezultatul să rămână în interiorul aceleiași alocări (sau exact după capătul ei), altfel apare UB chiar dacă nu dereferențiezi pointerul. `wrapping_add` nu are această cerință, dar pointerul rezultat poate fi folosit doar după ce revine în interiorul alocării.

## `transmute`: ultima soluție

`std::mem::transmute` reinterpretează biții unei valori ca alt tip de aceeași mărime. Aproape întotdeauna există o alternativă sigură:

```rust
fn main() {
    let x = 1.5_f32;

    // Varianta sigură:
    let biti = x.to_bits();
    let inapoi = f32::from_bits(biti);

    // Varianta cu transmute, echivalentă aici, dar fără nicio protecție:
    // SAFETY: f32 și u32 au aceeași mărime, iar orice model de biți e un u32 valid
    let biti2: u32 = unsafe { std::mem::transmute(x) };

    println!("{biti:#x} {inapoi} {}", biti == biti2);

    let octeti = 0x12345678_u32.to_le_bytes(); // în loc de transmute::<u32, [u8; 4]>
    println!("{octeti:x?}");
}
```

Pericolele lui `transmute`: poate crea valori invalide (un `u8` cu valoarea 3 transformat în `bool`), poate prelungi lifetimes (`&'a T` → `&'static T`) și poate reinterpreta tipuri `repr(Rust)`, al căror layout nu e garantat.

## Callbacks: Rust ↔ C

O funcție C care primește un callback așteaptă un pointer la funcție `extern "C"`. Ca să transmiți și date, convenția este un `void*` de context:

```rust
use std::ffi::c_void;

// Simulăm o bibliotecă C: apelează `cb` pentru fiecare element.
extern "C" fn pentru_fiecare(date: *const i32, n: usize, cb: extern "C" fn(*mut c_void, i32), ctx: *mut c_void) {
    for i in 0..n {
        // SAFETY: apelantul garantează că `date` are `n` elemente
        cb(ctx, unsafe { *date.add(i) });
    }
}

extern "C" fn aduna_la_suma(ctx: *mut c_void, x: i32) {
    // SAFETY: `ctx` este un `&mut i64` transmis de noi mai jos
    let suma = unsafe { &mut *(ctx as *mut i64) };
    *suma += x as i64;
}

fn main() {
    let v = [1, 2, 3, 4];
    let mut suma: i64 = 0;
    pentru_fiecare(v.as_ptr(), v.len(), aduna_la_suma, &mut suma as *mut i64 as *mut c_void);
    println!("suma: {suma}");
}
```

## Ownership peste granița FFI

Cine alocă memoria trebuie s-o și elibereze, cu **același alocator**. Când dai un obiect Rust către C, folosești `Box::into_raw`, iar la întoarcere, `Box::from_raw`:

```rust
pub struct Contor {
    valoare: u64,
}

#[unsafe(no_mangle)]
pub extern "C" fn contor_nou() -> *mut Contor {
    Box::into_raw(Box::new(Contor { valoare: 0 })) // ownership-ul trece la C
}

#[unsafe(no_mangle)]
pub extern "C" fn contor_incrementeaza(c: *mut Contor) -> u64 {
    // SAFETY: `c` provine din `contor_nou` și nu a fost eliberat
    let c = unsafe { &mut *c };
    c.valoare += 1;
    c.valoare
}

#[unsafe(no_mangle)]
pub extern "C" fn contor_elibereaza(c: *mut Contor) {
    if !c.is_null() {
        // SAFETY: `c` provine din `contor_nou`, iar ownership-ul revine la Rust
        drop(unsafe { Box::from_raw(c) });
    }
}

fn main() {
    let c = contor_nou();
    contor_incrementeaza(c);
    println!("{}", contor_incrementeaza(c));
    contor_elibereaza(c);
}
```

## Trait-uri `unsafe`

Un trait `unsafe` are condiții pe care **implementarea** trebuie să le respecte. Cele mai cunoscute sunt `Send` și `Sync`. Le implementezi manual doar când compilatorul nu le poate deduce, de exemplu pentru un tip care conține pointeri bruți, dar sincronizează corect accesul:

```rust
struct Tampon {
    ptr: *mut u8, // pointerii bruți nu sunt Send/Sync
    len: usize,
}

// SAFETY: `Tampon` deține exclusiv memoria spre care arată `ptr`,
// deci poate fi mutat între thread-uri la fel ca un Box<[u8]>.
unsafe impl Send for Tampon {}

fn main() {
    let mut date = vec![1u8, 2, 3].into_boxed_slice();
    let t = Tampon { ptr: date.as_mut_ptr(), len: date.len() };
    let h = std::thread::spawn(move || t.len);
    println!("{}", h.join().unwrap());
    drop(date);
}
```

> **De reținut:** UB înseamnă că optimizatorul presupune că situația nu apare, deci nu e „doar un crash”. `add` trebuie să rămână în interiorul alocării. Evită `transmute` când există `to_bits`, `from_le_bytes` și altele. Callbacks în stil C folosesc `extern "C" fn` + `*mut c_void`. Memoria se eliberează de cine a alocat-o.
