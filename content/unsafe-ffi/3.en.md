# Unsafe and FFI — Advanced

What undefined behavior concretely is, how to use raw pointers correctly, why `transmute` is dangerous and how to pass callbacks between Rust and C.

## Undefined behavior (UB)

Correct `unsafe` code must **never** produce undefined behavior. A few common sources:

- dereferencing a null, misaligned or dangling pointer;
- breaking the aliasing rules: two active `&mut` to the same memory, or modifying through `&T` without `UnsafeCell`;
- an invalid value for its type: a `bool` with value 2, an invalid `char`, a null reference, a nonexistent enum value;
- reading uninitialized memory (except through `MaybeUninit`);
- a data race;
- a panic crossing an `extern "C"` boundary.

UB doesn't mean "it'll probably crash". It means **the compiler assumes it never happens** and optimizes based on that assumption. A program with UB can work perfectly in debug and wrongly in release.

## Pointer arithmetic

```rust
fn main() {
    let v = [10u32, 20, 30, 40];
    let p = v.as_ptr();

    // SAFETY: indexes 0..4 are inside the array
    unsafe {
        for i in 0..v.len() {
            print!("{} ", *p.add(i)); // `add` uses element units, not bytes
        }
    }
    println!();

    let end = p.wrapping_add(v.len()); // a pointer "one past the last element" is allowed
    // SAFETY: both pointers come from the same array
    println!("distance: {}", unsafe { end.offset_from(p) });
}
```

`add` / `offset` require the result to stay inside the same allocation (or exactly one past its end), otherwise it's UB even if you don't dereference the pointer. `wrapping_add` doesn't have this requirement, but the resulting pointer can be used only once it's back inside the allocation.

## `transmute`: the last resort

`std::mem::transmute` reinterprets the bits of a value as another type of the same size. There's almost always a safe alternative:

```rust
fn main() {
    let x = 1.5_f32;

    // The safe way:
    let bits = x.to_bits();
    let back = f32::from_bits(bits);

    // The transmute way, equivalent here, but with no protection at all:
    // SAFETY: f32 and u32 have the same size, and every bit pattern is a valid u32
    let bits2: u32 = unsafe { std::mem::transmute(x) };

    println!("{bits:#x} {back} {}", bits == bits2);

    let bytes = 0x12345678_u32.to_le_bytes(); // instead of transmute::<u32, [u8; 4]>
    println!("{bytes:x?}");
}
```

The dangers of `transmute`: it can create invalid values (a `u8` with value 3 turned into a `bool`), it can extend lifetimes (`&'a T` → `&'static T`), and it can reinterpret `repr(Rust)` types, whose layout isn't guaranteed.

## Callbacks: Rust ↔ C

A C function that takes a callback expects an `extern "C"` function pointer. To pass data as well, the convention is a `void*` context:

```rust
use std::ffi::c_void;

// We simulate a C library: it calls `cb` for each element.
extern "C" fn for_each(data: *const i32, n: usize, cb: extern "C" fn(*mut c_void, i32), ctx: *mut c_void) {
    for i in 0..n {
        // SAFETY: the caller guarantees `data` has `n` elements
        cb(ctx, unsafe { *data.add(i) });
    }
}

extern "C" fn add_to_sum(ctx: *mut c_void, x: i32) {
    // SAFETY: `ctx` is a `&mut i64` passed by us below
    let sum = unsafe { &mut *(ctx as *mut i64) };
    *sum += x as i64;
}

fn main() {
    let v = [1, 2, 3, 4];
    let mut sum: i64 = 0;
    for_each(v.as_ptr(), v.len(), add_to_sum, &mut sum as *mut i64 as *mut c_void);
    println!("sum: {sum}");
}
```

## Ownership across the FFI boundary

Whoever allocates the memory must also free it, with **the same allocator**. When you hand a Rust object to C, you use `Box::into_raw`, and on the way back, `Box::from_raw`:

```rust
pub struct Counter {
    value: u64,
}

#[unsafe(no_mangle)]
pub extern "C" fn counter_new() -> *mut Counter {
    Box::into_raw(Box::new(Counter { value: 0 })) // ownership goes to C
}

#[unsafe(no_mangle)]
pub extern "C" fn counter_increment(c: *mut Counter) -> u64 {
    // SAFETY: `c` comes from `counter_new` and hasn't been freed
    let c = unsafe { &mut *c };
    c.value += 1;
    c.value
}

#[unsafe(no_mangle)]
pub extern "C" fn counter_free(c: *mut Counter) {
    if !c.is_null() {
        // SAFETY: `c` comes from `counter_new`, and ownership returns to Rust
        drop(unsafe { Box::from_raw(c) });
    }
}

fn main() {
    let c = counter_new();
    counter_increment(c);
    println!("{}", counter_increment(c));
    counter_free(c);
}
```

## `unsafe` traits

An `unsafe` trait has conditions that the **implementation** must uphold. The best known are `Send` and `Sync`. You implement them by hand only when the compiler can't infer them, for example for a type that contains raw pointers but synchronizes access correctly:

```rust
struct Buffer {
    ptr: *mut u8, // raw pointers aren't Send/Sync
    len: usize,
}

// SAFETY: `Buffer` exclusively owns the memory `ptr` points to,
// so it can be moved between threads just like a Box<[u8]>.
unsafe impl Send for Buffer {}

fn main() {
    let mut data = vec![1u8, 2, 3].into_boxed_slice();
    let b = Buffer { ptr: data.as_mut_ptr(), len: data.len() };
    let h = std::thread::spawn(move || b.len);
    println!("{}", h.join().unwrap());
    drop(data);
}
```

> **Key takeaway:** UB means the optimizer assumes the situation never happens, so it's not "just a crash". `add` must stay inside the allocation. Avoid `transmute` when `to_bits`, `from_le_bytes` and the like exist. C-style callbacks use `extern "C" fn` + `*mut c_void`. Memory is freed by whoever allocated it.
