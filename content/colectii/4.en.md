# Collections — Expert

How the standard collections are built: the layout of a `Vec`, the growth strategy, SwissTable hash tables and B-trees.

## The layout of a `Vec<T>`

A `Vec<T>` has three words on the stack: a **pointer** to the heap buffer, the **capacity** and the **length**. `String` is a `Vec<u8>` with the invariant that its bytes are valid UTF-8. `Box<[T]>` has only two words (pointer and length), because it can no longer grow:

```rust
fn main() {
    println!("Vec<u8>:    {}", size_of::<Vec<u8>>());    // 24
    println!("String:     {}", size_of::<String>());     // 24
    println!("Box<[u8]>:  {}", size_of::<Box<[u8]>>());  // 16
    println!("Option<Vec<u8>>: {}", size_of::<Option<Vec<u8>>>()); // 24: the pointer is never null

    let v: Vec<u8> = Vec::new();
    println!("does Vec::new() allocate? capacity = {}", v.capacity()); // 0: no allocation
}
```

`Vec::new()` allocates nothing. The pointer is a "dangling" one, aligned and non-null (`NonNull::dangling()`). The first allocation happens on the first `push`.

## The growth strategy

The current implementation **doubles** the capacity on each reallocation, starting from a minimum that depends on the element size: 8 for 1-byte elements, 4 for elements of at most 1 KiB, 1 for the rest. The documentation **doesn't guarantee** the exact values, only that `push` is amortized O(1):

```rust
fn main() {
    let mut v: Vec<u64> = Vec::new();
    let mut last = v.capacity();
    for i in 0..100 {
        v.push(i);
        if v.capacity() != last {
            print!("{} ", v.capacity());
            last = v.capacity();
        }
    }
    println!();
}
```

A reallocation **moves** every element to a new address. That's why the borrow checker forbids holding a reference to an element while you `push`.

For zero-sized types, `Vec` never allocates, and the reported capacity is `usize::MAX`:

```rust
fn main() {
    let mut v = Vec::new();
    v.push(());
    v.push(());
    println!("len {}, capacity {}", v.len(), v.capacity() == usize::MAX);
}
```

## `HashMap`: SwissTable

`std::collections::HashMap` internally uses the **hashbrown** implementation, a port of Google's *SwissTable*:

- elements live directly in a single array (*open addressing*, no linked lists);
- a separate array of **control bytes** holds 7 bits of each slot's hash;
- a lookup compares 16 control bytes at once, with SIMD instructions, and checks the key only on a match.

The default hash function is **SipHash-1-3**, with a random key per process (`RandomState`). It protects you from HashDoS attacks, in which someone deliberately sends keys with the same hash, but it is slower than the alternatives. For small keys and trusted data, you can change the hasher:

```rust
use std::collections::HashMap;
use std::hash::{BuildHasherDefault, DefaultHasher};

fn main() {
    // DefaultHasher with a fixed key: deterministic across runs, useful in tests
    let mut m: HashMap<u32, &str, BuildHasherDefault<DefaultHasher>> = HashMap::default();
    m.insert(1, "one");
    m.insert(2, "two");
    println!("{:?}", m.get(&2));
}
```

In practice, crates such as `rustc-hash` (FxHash) or `ahash` are much faster for integer keys. The Rust compiler uses FxHash internally.

Because the hash key is random, **iteration order differs between runs**. Don't rely on it, not even in tests.

## `BTreeMap`: a B-tree

`BTreeMap` isn't a binary tree. Each node holds up to 11 keys (in the implementation, B = 6), stored contiguously. More keys per node means fewer jumps through memory and better cache usage than a red-black tree.

## Iterator invalidation can't happen

In C++, modifying a `std::vector` while you iterate over it is undefined behavior. In Rust, the same mistake is a compile error, because the iterator holds a borrow of the collection:

```rust,compile_fail
fn main() {
    let mut v = vec![1, 2, 3];
    for x in &v {
        if *x == 2 {
            v.push(4); // error E0502: `v` is already borrowed by the iterator
        }
    }
}
```

The idiomatic solutions: collect the changes into a separate vector and apply them after the loop, use `retain` or `extend`, or iterate with indexes if the algorithm really requires it.

## `shrink_to_fit` and `into_boxed_slice`

Once you've finished building a large collection, you can release the unused capacity:

```rust
fn main() {
    let mut v = Vec::with_capacity(1000);
    v.extend(0..10);
    v.shrink_to_fit();
    println!("capacity after shrink: {}", v.capacity()); // 10
    let fixed: Box<[i32]> = v.into_boxed_slice(); // fixed length, 16 bytes on the stack
    println!("{}", fixed.len());
}
```

> **Key takeaway:** `Vec` = (pointer, capacity, length), with geometric growth whose exact values aren't guaranteed. `HashMap` is a SwissTable with SipHash and random iteration order. `BTreeMap` is a B-tree with wide nodes. The borrow checker makes iterator invalidation impossible.
