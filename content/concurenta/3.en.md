# Concurrency — Advanced

How the type system guarantees the absence of data races, plus atomics, condition variables and mutex poisoning.

## `Send` and `Sync`: the compile-time guarantee

- `T: Send`: a `T` value can be **moved** to another thread.
- `T: Sync`: a `&T` reference can be **shared** between threads. Equivalently: `&T` is `Send`.

The compiler infers them automatically from the fields. A few examples:

| Type | `Send` | `Sync` | Why |
|---|---|---|---|
| `i32`, `String`, `Vec<T>` | yes | yes | plain data |
| `Rc<T>` | no | no | the counter isn't atomic |
| `Arc<T>` (with `T: Send + Sync`) | yes | yes | atomic counter |
| `Cell<T>`, `RefCell<T>` | yes | **no** | modification through `&` without synchronization |
| `Mutex<T>` (with `T: Send`) | yes | yes | synchronizes access |
| `MutexGuard<T>` | **no** | yes | some systems require unlocking on the same thread |

`thread::spawn` requires `F: Send + 'static`. Any attempt to send something unsafe is a **compile error**. That's how Rust eliminates data races in safe code.

## Data race vs. race condition

- A **data race** happens when two threads access the same memory, at least one of them writes, and there's no synchronization. It's undefined behavior, and in safe Rust it's **impossible**.
- A **race condition** is a logic error: the result depends on the order of operations. Rust **can't** prevent it:

```rust
use std::sync::atomic::{AtomicU32, Ordering};
use std::thread;

static BALANCE: AtomicU32 = AtomicU32::new(100);

fn withdraw_wrong(amount: u32) -> bool {
    // check and subtract separately: another thread can step in between
    if BALANCE.load(Ordering::SeqCst) >= amount {
        BALANCE.fetch_sub(amount, Ordering::SeqCst);
        true
    } else {
        false
    }
}

fn withdraw_right(amount: u32) -> bool {
    // check and subtract in a single atomic operation
    BALANCE.fetch_update(Ordering::SeqCst, Ordering::SeqCst, |b| b.checked_sub(amount)).is_ok()
}

fn main() {
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| withdraw_right(30));
        }
    });
    println!("final balance: {}", BALANCE.load(Ordering::SeqCst)); // 10: only 3 withdrawals succeed
    let _ = withdraw_wrong; // the wrong version can go below zero: atomics don't panic, they wrap to a huge value
}
```

## Atomics

The types in `std::sync::atomic` (`AtomicBool`, `AtomicUsize`, `AtomicI64`…) allow indivisible operations without a lock: `load`, `store`, `fetch_add`, `swap`, `compare_exchange`. They suit counters, flags and statistics:

```rust
use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
use std::thread;
use std::time::Duration;

fn main() {
    let stop = AtomicBool::new(false);
    let processed = AtomicUsize::new(0);

    thread::scope(|s| {
        for _ in 0..3 {
            s.spawn(|| {
                while !stop.load(Ordering::Relaxed) {
                    processed.fetch_add(1, Ordering::Relaxed);
                    thread::sleep(Duration::from_millis(1));
                }
            });
        }
        thread::sleep(Duration::from_millis(20));
        stop.store(true, Ordering::Relaxed);
    });

    println!("processed anything? {}", processed.load(Ordering::Relaxed) > 0);
}
```

`Ordering` describes the memory-ordering guarantees. For independent counters, `Relaxed` is enough. The details are at the Expert level.

## `Condvar`: wait for a condition

A condition variable lets a thread **sleep** until another one tells it something has changed. It's always used together with a `Mutex`, in a loop, because spurious wakeups can happen:

```rust
use std::sync::{Arc, Condvar, Mutex};
use std::thread;

fn main() {
    let pair = Arc::new((Mutex::new(false), Condvar::new()));
    let p2 = Arc::clone(&pair);

    thread::spawn(move || {
        let (ready, cv) = &*p2;
        *ready.lock().unwrap() = true;
        cv.notify_one();
    });

    let (ready, cv) = &*pair;
    let mut g = ready.lock().unwrap();
    while !*g {
        g = cv.wait(g).unwrap(); // releases the lock while sleeping
    }
    println!("signal received");
}
```

## Mutex poisoning

If a thread panics while holding a `Mutex`, the data may be left half-modified. The mutex becomes **poisoned**, and `lock()` returns `Err` on subsequent attempts:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let data = Arc::new(Mutex::new(vec![1, 2]));
    let d = Arc::clone(&data);
    std::panic::set_hook(Box::new(|_| {})); // hide the panic message, for the example
    let _ = thread::spawn(move || {
        let mut v = d.lock().unwrap();
        v.push(3);
        panic!("failure in the middle of the update");
    })
    .join();

    match data.lock() {
        Ok(v) => println!("ok: {v:?}"),
        Err(poisoned) => {
            let v = poisoned.into_inner(); // you can recover the data, at your own risk
            println!("poisoned mutex, data: {v:?}");
        }
    }
}
```

`.lock().unwrap()` propagates the panic further, and most of the time that's the right choice.

> **Key takeaway:** `Send` and `Sync` make data races impossible in safe Rust, but logical race conditions are still possible. Atomics offer indivisible operations without a lock. `Condvar` is used with a `Mutex`, in a loop. A panic while holding a `Mutex` poisons it.
