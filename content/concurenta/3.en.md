# Concurență — Avansat

Cum garantează sistemul de tipuri lipsa curselor de date, plus atomicele, variabilele de condiție și otrăvirea mutex-urilor.

## `Send` și `Sync`: garanția de la compilare

- `T: Send`: o valoare `T` poate fi **mutată** în alt thread.
- `T: Sync`: o referință `&T` poate fi **partajată** între thread-uri. Echivalent: `&T` este `Send`.

Compilatorul le deduce automat din câmpuri. Câteva exemple:

| Tip | `Send` | `Sync` | De ce |
|---|---|---|---|
| `i32`, `String`, `Vec<T>` | da | da | date simple |
| `Rc<T>` | nu | nu | contorul nu e atomic |
| `Arc<T>` (cu `T: Send + Sync`) | da | da | contor atomic |
| `Cell<T>`, `RefCell<T>` | da | **nu** | modificare prin `&` fără sincronizare |
| `Mutex<T>` (cu `T: Send`) | da | da | sincronizează accesul |
| `MutexGuard<T>` | **nu** | da | unele sisteme cer deblocarea pe același thread |

`thread::spawn` cere `F: Send + 'static`. Orice încercare de a trimite ceva nesigur e o **eroare de compilare**. Așa elimină Rust cursele de date în codul safe.

## Cursă de date vs. race condition

- O **cursă de date** (*data race*) apare când două thread-uri accesează aceeași memorie, cel puțin unul scrie și nu există sincronizare. Este comportament nedefinit, iar în Rust safe e **imposibilă**.
- O **race condition** este o eroare de logică: rezultatul depinde de ordinea operațiilor. Rust **nu** o poate preveni:

```rust
use std::sync::atomic::{AtomicU32, Ordering};
use std::thread;

static SOLD: AtomicU32 = AtomicU32::new(100);

fn retrage_gresit(suma: u32) -> bool {
    // verificare și scădere separate: alt thread poate interveni între ele
    if SOLD.load(Ordering::SeqCst) >= suma {
        SOLD.fetch_sub(suma, Ordering::SeqCst);
        true
    } else {
        false
    }
}

fn retrage_corect(suma: u32) -> bool {
    // verificare și scădere într-o singură operație atomică
    SOLD.fetch_update(Ordering::SeqCst, Ordering::SeqCst, |s| s.checked_sub(suma)).is_ok()
}

fn main() {
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| retrage_corect(30));
        }
    });
    println!("sold final: {}", SOLD.load(Ordering::SeqCst)); // 10: doar 3 retrageri reușesc
    let _ = retrage_gresit; // versiunea greșită poate scădea sub zero: atomicele nu dau panic, ci se întorc la o valoare uriașă
}
```

## Atomice

Tipurile din `std::sync::atomic` (`AtomicBool`, `AtomicUsize`, `AtomicI64`…) permit operații indivizibile fără lacăt: `load`, `store`, `fetch_add`, `swap`, `compare_exchange`. Sunt potrivite pentru contoare, flag-uri și statistici:

```rust
use std::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
use std::thread;
use std::time::Duration;

fn main() {
    let opreste = AtomicBool::new(false);
    let procesate = AtomicUsize::new(0);

    thread::scope(|s| {
        for _ in 0..3 {
            s.spawn(|| {
                while !opreste.load(Ordering::Relaxed) {
                    procesate.fetch_add(1, Ordering::Relaxed);
                    thread::sleep(Duration::from_millis(1));
                }
            });
        }
        thread::sleep(Duration::from_millis(20));
        opreste.store(true, Ordering::Relaxed);
    });

    println!("procesat ceva? {}", procesate.load(Ordering::Relaxed) > 0);
}
```

`Ordering` descrie garanțiile de ordonare a memoriei. Pentru contoare independente, `Relaxed` e suficient. Detaliile sunt la nivelul Expert.

## `Condvar`: așteaptă o condiție

O variabilă de condiție lasă un thread să **doarmă** până când altul îl anunță că s-a schimbat ceva. Se folosește mereu împreună cu un `Mutex`, într-o buclă, pentru că pot apărea treziri false:

```rust
use std::sync::{Arc, Condvar, Mutex};
use std::thread;

fn main() {
    let pereche = Arc::new((Mutex::new(false), Condvar::new()));
    let p2 = Arc::clone(&pereche);

    thread::spawn(move || {
        let (gata, cv) = &*p2;
        *gata.lock().unwrap() = true;
        cv.notify_one();
    });

    let (gata, cv) = &*pereche;
    let mut g = gata.lock().unwrap();
    while !*g {
        g = cv.wait(g).unwrap(); // eliberează lacătul cât doarme
    }
    println!("semnal primit");
}
```

## Otrăvirea mutex-ului (*poisoning*)

Dacă un thread dă panic în timp ce ține un `Mutex`, datele pot fi rămas pe jumătate modificate. Mutex-ul devine **otrăvit**, iar `lock()` returnează `Err` la următoarele încercări:

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let date = Arc::new(Mutex::new(vec![1, 2]));
    let d = Arc::clone(&date);
    std::panic::set_hook(Box::new(|_| {})); // ascunde mesajul de panic, pentru exemplu
    let _ = thread::spawn(move || {
        let mut v = d.lock().unwrap();
        v.push(3);
        panic!("eșec în mijlocul modificării");
    })
    .join();

    match date.lock() {
        Ok(v) => println!("ok: {v:?}"),
        Err(otravit) => {
            let v = otravit.into_inner(); // poți recupera datele, pe răspunderea ta
            println!("mutex otrăvit, date: {v:?}");
        }
    }
}
```

`.lock().unwrap()` propagă panic-ul mai departe, iar de cele mai multe ori asta e alegerea corectă.

> **De reținut:** `Send` și `Sync` fac cursele de date imposibile în Rust safe, dar race conditions logice rămân posibile. Atomicele oferă operații indivizibile fără lacăt. `Condvar` se folosește cu un `Mutex`, într-o buclă. Un panic în timp ce ții un `Mutex` îl otrăvește.
