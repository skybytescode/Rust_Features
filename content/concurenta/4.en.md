# Concurență — Expert

Modelul de memorie: ce înseamnă exact fiecare `Ordering`, cum construiești un spinlock, ce e *false sharing* și cum testezi cod concurent.

## De ce există `Ordering`

Atât compilatorul, cât și procesorul **reordonează** operațiile pe memorie, cât timp un singur thread nu poate observa diferența. Între thread-uri, reordonările devin vizibile. `Ordering` spune ce garanții de ordonare ceri pentru o operație atomică.

Rust folosește modelul de memorie din C++20:

| Ordering | Garanție |
|---|---|
| `Relaxed` | doar atomicitatea operației, fără ordonare față de alte accese |
| `Release` (la scriere) | nimic din fața ei nu poate fi mutat după ea |
| `Acquire` (la citire) | nimic de după ea nu poate fi mutat înaintea ei |
| `AcqRel` | ambele, pentru operații citire-modificare-scriere |
| `SeqCst` | în plus, o ordine totală unică, văzută la fel de toate thread-urile |

## Release / Acquire: relația *happens-before*

Dacă thread-ul A face un `store(Release)`, iar thread-ul B face un `load(Acquire)` care **vede** acea valoare, atunci tot ce a scris A înainte de store este vizibil pentru B după load. E mecanismul prin care „publici” date:

```rust
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};
use std::thread;

static DATE: AtomicU64 = AtomicU64::new(0);
static GATA: AtomicBool = AtomicBool::new(false);

fn main() {
    thread::scope(|s| {
        s.spawn(|| {
            DATE.store(42, Ordering::Relaxed);    // (1)
            GATA.store(true, Ordering::Release);  // (2): publică tot ce e înainte
        });
        s.spawn(|| {
            while !GATA.load(Ordering::Acquire) { // (3): sincronizează cu (2)
                std::hint::spin_loop();
            }
            // garantat 42: (1) happens-before (2), care se sincronizează cu (3)
            println!("{}", DATE.load(Ordering::Relaxed));
        });
    });
}
```

Cu `Relaxed` la (2) și (3), programul ar putea afișa 0 pe arhitecturi cu memorie „slabă” (ARM, POWER). Pe x86 tot ar funcționa, din întâmplare, pentru că arhitectura are o ordonare mai puternică. Așa ajung bug-urile concurente să apară doar pe telefoane sau servere ARM.

## Un spinlock

Un spinlock minimal arată cum se combină `compare_exchange` cu `Acquire` / `Release`:

```rust
use std::cell::UnsafeCell;
use std::ops::{Deref, DerefMut};
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

pub struct SpinLock<T> {
    blocat: AtomicBool,
    valoare: UnsafeCell<T>,
}

// SAFETY: accesul la `valoare` e exclusiv cât timp `blocat` e true
unsafe impl<T: Send> Sync for SpinLock<T> {}

pub struct Garda<'a, T> {
    lock: &'a SpinLock<T>,
}

impl<T> SpinLock<T> {
    pub const fn new(v: T) -> Self {
        SpinLock { blocat: AtomicBool::new(false), valoare: UnsafeCell::new(v) }
    }

    pub fn lock(&self) -> Garda<'_, T> {
        while self
            .blocat
            .compare_exchange_weak(false, true, Ordering::Acquire, Ordering::Relaxed)
            .is_err()
        {
            std::hint::spin_loop(); // indiciu pentru CPU: suntem într-o buclă de așteptare
        }
        Garda { lock: self }
    }
}

impl<T> Deref for Garda<'_, T> {
    type Target = T;
    // SAFETY: deținem lacătul
    fn deref(&self) -> &T { unsafe { &*self.lock.valoare.get() } }
}

impl<T> DerefMut for Garda<'_, T> {
    // SAFETY: deținem lacătul, deci accesul e exclusiv
    fn deref_mut(&mut self) -> &mut T { unsafe { &mut *self.lock.valoare.get() } }
}

impl<T> Drop for Garda<'_, T> {
    fn drop(&mut self) {
        self.lock.blocat.store(false, Ordering::Release); // publică modificările
    }
}

fn main() {
    let lista = SpinLock::new(Vec::new());
    thread::scope(|s| {
        for i in 0..4 {
            let lista = &lista;
            s.spawn(move || {
                for j in 0..100 {
                    lista.lock().push(i * 100 + j);
                }
            });
        }
    });
    println!("{} elemente", lista.lock().len()); // 400
}
```

`compare_exchange_weak` poate eșua fals pe unele arhitecturi, dar e mai ieftin într-o buclă. În cod real, un spinlock e rareori alegerea bună: `std::sync::Mutex` folosește *futex*-uri pe Linux și adoarme thread-ul în loc să consume CPU.

## False sharing

Procesoarele sincronizează memoria pe **linii de cache**, de obicei de 64 de octeți. Două atomice independente aflate pe aceeași linie se încetinesc reciproc, chiar dacă thread-uri diferite le modifică separat. Soluția este alinierea:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::thread;
use std::time::Instant;

#[repr(align(64))] // fiecare contor pe propria linie de cache
struct Aliniat(AtomicU64);

fn main() {
    let lipite = [AtomicU64::new(0), AtomicU64::new(0)];
    let separate = [Aliniat(AtomicU64::new(0)), Aliniat(AtomicU64::new(0))];

    let t = Instant::now();
    thread::scope(|s| {
        for c in &lipite {
            s.spawn(move || for _ in 0..2_000_000 { c.fetch_add(1, Ordering::Relaxed); });
        }
    });
    let lipit = t.elapsed();

    let t = Instant::now();
    thread::scope(|s| {
        for c in &separate {
            s.spawn(move || for _ in 0..2_000_000 { c.0.fetch_add(1, Ordering::Relaxed); });
        }
    });
    let separat = t.elapsed();

    println!("aceeași linie: {lipit:?}, linii separate: {separat:?}");
    println!("mărime Aliniat: {}", size_of::<Aliniat>());
}
```

Diferența depinde de procesor și poate fi de câteva ori. Crate-ul `crossbeam` oferă `CachePadded<T>` pentru același scop.

## Testarea codului concurent

Bug-urile de ordonare apar rar și greu de reprodus. Câteva unelte te ajută:

- **Miri** (`cargo +nightly miri test`) detectează cursele de date și explorează unele reordonări permise de modelul de memorie;
- **loom** rulează un test în toate interleaving-urile posibile ale thread-urilor (pentru structuri mici);
- **ThreadSanitizer** (`RUSTFLAGS="-Z sanitizer=thread"`, nightly) detectează cursele la runtime.

> **De reținut:** `Release` publică, `Acquire` primește, iar împreună creează *happens-before*. `Relaxed` garantează doar atomicitatea. Pe x86 greșelile de ordonare se văd rar, pe ARM des. Separă atomicele fierbinți pe linii de cache diferite și testează cu Miri sau loom.
