# Concurrency — Expert

The memory model: what exactly each `Ordering` means, how to build a spinlock, what *false sharing* is and how to test concurrent code.

## Why `Ordering` exists

Both the compiler and the processor **reorder** memory operations, as long as a single thread can't observe the difference. Between threads, reorderings become visible. `Ordering` says which ordering guarantees you ask for on an atomic operation.

Rust uses the C++20 memory model:

| Ordering | Guarantee |
|---|---|
| `Relaxed` | only the atomicity of the operation, no ordering relative to other accesses |
| `Release` (on a store) | nothing before it can be moved after it |
| `Acquire` (on a load) | nothing after it can be moved before it |
| `AcqRel` | both, for read-modify-write operations |
| `SeqCst` | additionally, a single total order seen the same way by every thread |

## Release / Acquire: the *happens-before* relationship

If thread A does a `store(Release)`, and thread B does a `load(Acquire)` that **sees** that value, then everything A wrote before the store is visible to B after the load. It's the mechanism by which you "publish" data:

```rust
use std::sync::atomic::{AtomicBool, AtomicU64, Ordering};
use std::thread;

static DATA: AtomicU64 = AtomicU64::new(0);
static READY: AtomicBool = AtomicBool::new(false);

fn main() {
    thread::scope(|s| {
        s.spawn(|| {
            DATA.store(42, Ordering::Relaxed);     // (1)
            READY.store(true, Ordering::Release);  // (2): publishes everything before it
        });
        s.spawn(|| {
            while !READY.load(Ordering::Acquire) { // (3): synchronizes with (2)
                std::hint::spin_loop();
            }
            // guaranteed 42: (1) happens-before (2), which synchronizes with (3)
            println!("{}", DATA.load(Ordering::Relaxed));
        });
    });
}
```

With `Relaxed` at (2) and (3), the program could print 0 on architectures with "weak" memory (ARM, POWER). On x86 it would still work, by accident, because the architecture has stronger ordering. That's how concurrency bugs end up showing only on phones or ARM servers.

## A spinlock

A minimal spinlock shows how `compare_exchange` combines with `Acquire` / `Release`:

```rust
use std::cell::UnsafeCell;
use std::ops::{Deref, DerefMut};
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

pub struct SpinLock<T> {
    locked: AtomicBool,
    value: UnsafeCell<T>,
}

// SAFETY: access to `value` is exclusive while `locked` is true
unsafe impl<T: Send> Sync for SpinLock<T> {}

pub struct Guard<'a, T> {
    lock: &'a SpinLock<T>,
}

impl<T> SpinLock<T> {
    pub const fn new(v: T) -> Self {
        SpinLock { locked: AtomicBool::new(false), value: UnsafeCell::new(v) }
    }

    pub fn lock(&self) -> Guard<'_, T> {
        while self
            .locked
            .compare_exchange_weak(false, true, Ordering::Acquire, Ordering::Relaxed)
            .is_err()
        {
            std::hint::spin_loop(); // hint to the CPU: we're in a wait loop
        }
        Guard { lock: self }
    }
}

impl<T> Deref for Guard<'_, T> {
    type Target = T;
    // SAFETY: we hold the lock
    fn deref(&self) -> &T { unsafe { &*self.lock.value.get() } }
}

impl<T> DerefMut for Guard<'_, T> {
    // SAFETY: we hold the lock, so access is exclusive
    fn deref_mut(&mut self) -> &mut T { unsafe { &mut *self.lock.value.get() } }
}

impl<T> Drop for Guard<'_, T> {
    fn drop(&mut self) {
        self.lock.locked.store(false, Ordering::Release); // publishes the changes
    }
}

fn main() {
    let list = SpinLock::new(Vec::new());
    thread::scope(|s| {
        for i in 0..4 {
            let list = &list;
            s.spawn(move || {
                for j in 0..100 {
                    list.lock().push(i * 100 + j);
                }
            });
        }
    });
    println!("{} elements", list.lock().len()); // 400
}
```

`compare_exchange_weak` can fail spuriously on some architectures, but it's cheaper in a loop. In real code, a spinlock is rarely the right choice: `std::sync::Mutex` uses *futexes* on Linux and puts the thread to sleep instead of burning CPU.

## False sharing

Processors synchronize memory in **cache lines**, usually 64 bytes. Two independent atomics on the same line slow each other down, even if different threads modify them separately. The solution is alignment:

```rust
use std::sync::atomic::{AtomicU64, Ordering};
use std::thread;
use std::time::Instant;

#[repr(align(64))] // each counter on its own cache line
struct Aligned(AtomicU64);

fn main() {
    let packed = [AtomicU64::new(0), AtomicU64::new(0)];
    let separate = [Aligned(AtomicU64::new(0)), Aligned(AtomicU64::new(0))];

    let t = Instant::now();
    thread::scope(|s| {
        for c in &packed {
            s.spawn(move || for _ in 0..2_000_000 { c.fetch_add(1, Ordering::Relaxed); });
        }
    });
    let same_line = t.elapsed();

    let t = Instant::now();
    thread::scope(|s| {
        for c in &separate {
            s.spawn(move || for _ in 0..2_000_000 { c.0.fetch_add(1, Ordering::Relaxed); });
        }
    });
    let separate_lines = t.elapsed();

    println!("same line: {same_line:?}, separate lines: {separate_lines:?}");
    println!("size of Aligned: {}", size_of::<Aligned>());
}
```

The difference depends on the processor and can be several times. The `crossbeam` crate offers `CachePadded<T>` for the same purpose.

## Testing concurrent code

Ordering bugs show up rarely and are hard to reproduce. A few tools help:

- **Miri** (`cargo +nightly miri test`) detects data races and explores some of the reorderings allowed by the memory model;
- **loom** runs a test under every possible interleaving of the threads (for small structures);
- **ThreadSanitizer** (`RUSTFLAGS="-Z sanitizer=thread"`, nightly) detects races at runtime.

> **Key takeaway:** `Release` publishes, `Acquire` receives, and together they create *happens-before*. `Relaxed` guarantees only atomicity. On x86, ordering mistakes rarely show, on ARM often. Put hot atomics on separate cache lines and test with Miri or loom.
