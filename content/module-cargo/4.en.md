# Modules and Cargo — Expert

What happens between `cargo build` and the final binary: compilation units, metadata, codegen units, LTO, feature unification and dependency resolution.

## The crate is the unit of compilation

`rustc` compiles **a whole crate** at once, not file by file like a C compiler. Modules are only internal organization: `mod x;` textually includes the file in the crate tree. Consequences:

- splitting a large crate into several crates allows compiling **in parallel** and smaller rebuilds;
- dependencies between crates must form an **acyclic** graph, while modules can refer to each other circularly.

## What compiling a library produces

For a dependency, `rustc` generates a `.rlib` file containing:

- the object code;
- the crate's **metadata**: types, signatures, traits, and the bodies of generic and `#[inline]` functions, so they can be instantiated by the crates that use them.

Cargo does **pipelining**: a dependent crate can start compiling as soon as the dependency's metadata is ready (`.rmeta`), without waiting for the object code. That's why `cargo check` uses only the metadata and is much faster.

## Codegen units and incremental compilation

Inside a crate, the code is split into **codegen units** (CGUs), optimized by LLVM in parallel:

| Profile | Default CGUs | Incremental |
|---|---|---|
| `dev` | 256 | yes |
| `release` | 16 | no |

More CGUs mean faster compilation but weaker optimization, because LLVM can't inline across them. `codegen-units = 1` gives the best code. **Incremental compilation** keeps intermediate results in `target/`, so a small change redoes only the affected parts.

## LTO (Link-Time Optimization)

Without LTO, each crate is optimized separately, and non-generic functions without `#[inline]` can't be inlined across crates. LTO postpones part of the optimization until link time:

| Option | Effect |
|---|---|
| `lto = false` (default) | only "thin local LTO" across the CGUs of the same crate |
| `lto = "thin"` | parallel whole-program LTO: a good gain at moderate cost |
| `lto = "fat"` / `true` | the whole program as a single module: slowest, sometimes fastest |

## Feature unification

In a dependency graph, a crate is compiled **once** per platform, with the **union** of all features requested by any dependent. The result: features must be **additive**, meaning enabling a feature must not break anyone else's code:

```toml
# crate A asks for: tokio = { version = "1", features = ["rt"] }
# crate B asks for: tokio = { version = "1", features = ["net"] }
# the result: tokio is compiled once, with ["rt", "net"]
```

Resolver `"2"` (the default since the 2021 edition) no longer unifies features between normal dependencies, `build-dependencies` and `dev-dependencies` that aren't built for the same target. Resolver `"3"` (the default in the 2024 edition, Rust 1.84) additionally prefers dependency versions compatible with the `rust-version` (MSRV) declared in the package.

## Several versions of the same crate

If two dependencies require **incompatible** versions (for example `rand 0.8` and `rand 0.9`), Cargo builds both. Their types are **different** to the compiler, so a `rand_0_8::Rng` can't be used where a `rand_0_9::Rng` is required. The resulting error looks absurd at first glance ("expected `Rng`, found `Rng`"). `cargo tree -d` shows the duplicates.

## Symbols and visibility at link time

Rust visibility (`pub`) is not the same as symbol visibility in the binary:

- private functions may still appear as symbols, with "mangled" names;
- `#[unsafe(no_mangle)]` exports a symbol with the exact name, and `extern "C"` fixes the calling convention;
- a `cdylib` (`crate-type = ["cdylib"]`) exports only the `no_mangle` symbols, for FFI. A Rust `dylib` has no stable ABI and is rarely used.

## Useful tools

```bash
cargo tree                    # the dependency graph
cargo tree -e features -i serde   # why a feature is enabled
cargo build --timings         # HTML report: how long each crate took
cargo +nightly udeps          # unused dependencies (external crate)
cargo vendor                  # copies the dependencies' sources locally
RUSTFLAGS="-C target-cpu=native" cargo build --release  # optimize for the current CPU
```

> **Key takeaway:** the crate is the unit of compilation, and smaller crates compile in parallel. Metadata enables pipelining and a fast `cargo check`. CGUs and LTO trade compile speed for code quality. Features are unified per crate and must be additive.
