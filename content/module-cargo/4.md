# Module și Cargo — Expert

Ce se întâmplă între `cargo build` și binarul final: unități de compilare, metadate, codegen units, LTO, unificarea features și rezolvarea dependențelor.

## Crate-ul este unitatea de compilare

`rustc` compilează **un crate întreg** deodată, nu fișier cu fișier ca un compilator C. Modulele sunt doar organizare internă: `mod x;` include textual fișierul în arborele crate-ului. Consecințe:

- împărțirea unui crate mare în mai multe crate-uri permite compilarea **în paralel** și recompilări mai mici;
- dependențele dintre crate-uri trebuie să formeze un graf **aciclic**, pe când între module poți avea referințe circulare.

## Ce produce compilarea unei biblioteci

Pentru o dependență, `rustc` generează un fișier `.rlib` care conține:

- codul obiect;
- **metadatele** crate-ului: tipurile, semnăturile, trait-urile și corpurile funcțiilor generice și `#[inline]`, ca să poată fi instanțiate de crate-urile care le folosesc.

Cargo face **pipelining**: un crate dependent poate începe compilarea imediat ce metadatele dependenței sunt gata (`.rmeta`), fără să aștepte codul obiect. De aceea, `cargo check` folosește doar metadatele și e mult mai rapid.

## Codegen units și compilare incrementală

În interiorul unui crate, codul e împărțit în **codegen units** (CGU), optimizate de LLVM în paralel:

| Profil | CGU implicit | Incremental |
|---|---|---|
| `dev` | 256 | da |
| `release` | 16 | nu |

Mai multe CGU înseamnă compilare mai rapidă, dar optimizare mai slabă, pentru că LLVM nu poate inline-ui între ele. `codegen-units = 1` dă cel mai bun cod. **Compilarea incrementală** păstrează în `target/` rezultatele intermediare, ca la o modificare mică să refacă doar părțile afectate.

## LTO (Link-Time Optimization)

Fără LTO, fiecare crate e optimizat separat, iar funcțiile non-generice fără `#[inline]` nu pot fi inline-uite între crate-uri. LTO amână o parte din optimizare până la linkare:

| Opțiune | Efect |
|---|---|
| `lto = false` (implicit) | doar „thin local LTO” între CGU-urile aceluiași crate |
| `lto = "thin"` | LTO paralel pe tot programul: câștig bun, cost moderat |
| `lto = "fat"` / `true` | tot programul ca un singur modul: cel mai lent, uneori cel mai rapid |

## Unificarea features

Într-un graf de dependențe, un crate e compilat **o singură dată** per platformă, cu **reuniunea** tuturor features cerute de oricare dependent. Rezultatul: features trebuie să fie **aditive**, adică activarea unei feature nu are voie să strice codul altcuiva:

```toml
# crate-ul A cere: tokio = { version = "1", features = ["rt"] }
# crate-ul B cere: tokio = { version = "1", features = ["net"] }
# rezultatul: tokio e compilat o dată, cu ["rt", "net"]
```

Resolver-ul `"2"` (implicit din ediția 2021) nu mai unifică features între dependențele normale, `build-dependencies` și `dev-dependencies` care nu se compilează pentru același scop. Resolver-ul `"3"` (implicit în ediția 2024, Rust 1.84) preferă, în plus, versiunile de dependențe compatibile cu `rust-version` (MSRV) declarat în pachet.

## Mai multe versiuni ale aceluiași crate

Dacă două dependențe cer versiuni **incompatibile** (de exemplu `rand 0.8` și `rand 0.9`), Cargo le compilează pe amândouă. Tipurile lor sunt **diferite** pentru compilator, așa că un `rand_0_8::Rng` nu poate fi folosit unde se cere `rand_0_9::Rng`. Eroarea rezultată pare absurdă la prima vedere („expected `Rng`, found `Rng`”). `cargo tree -d` arată duplicatele.

## Simboluri și vizibilitate la linkare

Vizibilitatea Rust (`pub`) nu e același lucru cu vizibilitatea simbolurilor în binar:

- funcțiile private pot apărea totuși ca simboluri, cu nume „mangled”;
- `#[unsafe(no_mangle)]` exportă un simbol cu numele exact, iar `extern "C"` fixează convenția de apel;
- un `cdylib` (`crate-type = ["cdylib"]`) exportă doar simbolurile `no_mangle`, pentru FFI. Un `dylib` Rust nu are ABI stabil și se folosește rar.

## Unelte utile

```bash
cargo tree                    # graful de dependențe
cargo tree -e features -i serde   # de ce e activată o feature
cargo build --timings         # raport HTML: ce crate a durat cât
cargo +nightly udeps          # dependențe nefolosite (crate extern)
cargo vendor                  # copiază sursele dependențelor local
RUSTFLAGS="-C target-cpu=native" cargo build --release  # optimizare pentru CPU-ul curent
```

> **De reținut:** crate-ul este unitatea de compilare, iar crate-urile mai mici se compilează în paralel. Metadatele permit pipelining și `cargo check` rapid. CGU și LTO schimbă viteza de compilare pe calitatea codului. Features se unifică per crate și trebuie să fie aditive.
