# Modules and Cargo — Practitioner

How to organize a real project: library plus binary, visibility levels, re-exports, versions and workspaces.

## A library and a binary in the same project

A package can contain a library (`src/lib.rs`) and one or more binaries. The logic lives in the library, and `main.rs` only uses it. This structure makes the code easy to test and reuse:

```text
calculator/
├── Cargo.toml
└── src/
    ├── lib.rs          // pub fn evaluate(...)
    ├── main.rs         // use calculator::evaluate;
    └── bin/
        └── repl.rs     // a second binary: cargo run --bin repl
```

## Visibility levels

| Syntax | Visible in |
|---|---|
| (nothing) | the current module and its submodules |
| `pub(super)` | the parent module |
| `pub(crate)` | the whole crate, but not outside it |
| `pub` | anywhere, including other crates |

```rust
mod bank {
    pub struct Account {
        pub holder: String,      // public
        pub(crate) id: u32,      // visible in the whole crate
        balance: i64,            // private
    }

    impl Account {
        pub fn new(holder: &str) -> Self {
            Account { holder: holder.into(), id: 1, balance: 0 }
        }
        pub fn balance(&self) -> i64 {
            self.balance
        }
    }
}

fn main() {
    let a = bank::Account::new("Ana");
    println!("{} #{} balance {}", a.holder, a.id, a.balance());
    // a.balance = 1_000_000; // error: the field is private
}
```

## Re-exports with `pub use`

The internal file structure doesn't have to be the structure of the public API. With `pub use`, you expose items where it's convenient for the user:

```rust
mod internal {
    pub mod formats {
        pub mod json {
            pub fn serialize() -> &'static str { "{}" }
        }
    }
}

// the user writes `serialize()`, not `internal::formats::json::serialize()`
pub use internal::formats::json::serialize;

fn main() {
    println!("{}", serialize());
}
```

## Versions and `Cargo.lock`

Cargo uses **semantic versioning** (SemVer): `MAJOR.MINOR.PATCH`. In `Cargo.toml`, `serde = "1.0.200"` means "any compatible version", that is `>=1.0.200, <2.0.0`:

| Written | Accepts |
|---|---|
| `"1.2.3"` or `"^1.2.3"` | `>=1.2.3, <2.0.0` |
| `"0.4.1"` | `>=0.4.1, <0.5.0` (below 1.0, the minor counts as major) |
| `"~1.2.3"` | `>=1.2.3, <1.3.0` |
| `"=1.2.3"` | exactly 1.2.3 |

`Cargo.lock` records the **exact** versions chosen, so the build is reproducible. Commit it to git. That's the current recommendation for both applications and libraries. `cargo update` updates it within the limits in `Cargo.toml`.

## Features: optional functionality

```toml
[features]
default = ["json"]
json = ["dep:serde_json"]
compression = []

[dependencies]
serde_json = { version = "1", optional = true }
```

In code, you compile conditionally with `cfg`:

```rust
#[cfg(feature = "compression")]
fn compress(data: &[u8]) -> Vec<u8> {
    data.to_vec() // real implementation here
}

fn main() {
    #[cfg(feature = "compression")]
    println!("{:?}", compress(b"abc"));

    #[cfg(not(feature = "compression"))]
    println!("built without compression");
}
```

## Workspaces

A **workspace** groups several packages that share the same `Cargo.lock` and the same `target/` directory:

```toml
# root Cargo.toml
[workspace]
members = ["core", "cli", "server"]
resolver = "3"

[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
```

```toml
# cli/Cargo.toml
[dependencies]
core = { path = "../core" }
serde = { workspace = true }   # the same version everywhere
```

> **Key takeaway:** put the logic in `lib.rs` and only use it from `main.rs`. `pub(crate)` is the most useful visibility level for internal details. `pub use` builds a clean public API. Commit `Cargo.lock`, use features for optional parts and workspaces for several packages.
