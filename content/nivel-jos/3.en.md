# Low-level Rust — Advanced

What you have to provide yourself without `std`, how to access hardware registers, first steps with inline assembly, and how to use the processor's SIMD instructions.

## What you must define in a `no_std` binary

A `no_std` program that runs directly on hardware must provide what `std` usually offered:

- a **`#[panic_handler]`**: what happens on a panic (halt, reset, a message over UART);
- an **entry point**, with `#![no_main]`: the platform's startup code or a crate like `cortex-m-rt`;
- a **global allocator**, only if you use `alloc`;
- a **linker script** that says where the Flash memory and the RAM are.

```rust,ignore
#![no_std]
#![no_main]

use core::panic::PanicInfo;

#[panic_handler]
fn on_panic(_info: &PanicInfo) -> ! {
    // on real hardware: light an error LED or reset the chip
    loop {
        core::hint::spin_loop();
    }
}

#[unsafe(no_mangle)]
pub extern "C" fn _start() -> ! {
    // the startup code: initialize memory, then run the application
    loop {}
}
```

Without `std` there's no unwinding either: the profile must use `panic = "abort"`.

## Hardware registers: `volatile` accesses

Peripherals (GPIO, timers, UART) are controlled through **memory-mapped registers** (*MMIO*): fixed addresses where reading or writing has effects in hardware. The compiler must not remove, merge or reorder these accesses. That's why you use `read_volatile` and `write_volatile`:

```rust
use core::ptr;

// We simulate a register. On real hardware, it would be a fixed address, for example 0x4002_0014
fn main() {
    let mut register: u32 = 0;
    let address: *mut u32 = &mut register;

    // SAFETY: `address` is valid and aligned, and nobody else accesses it
    unsafe {
        ptr::write_volatile(address, 1 << 5);                // "turn on pin 5"
        let value = ptr::read_volatile(address);
        ptr::write_volatile(address, value | (1 << 3));      // and pin 3
        println!("{:#010b}", ptr::read_volatile(address));
    }
}
```

Without `volatile`, the compiler could keep only the last write, because to it the intermediate value "isn't read by anyone". In practice, PAC crates generated with `svd2rust` wrap these accesses in safe APIs, for each register.

## Inline assembly: `asm!`

The `asm!` macro (stable since Rust 1.59) inserts processor instructions directly into the code. The compiler allocates the registers for the operands:

```rust
#[cfg(target_arch = "x86_64")]
fn add_asm(a: u64, b: u64) -> u64 {
    let result: u64;
    // SAFETY: the instruction only adds two registers, with no effects on memory
    unsafe {
        core::arch::asm!(
            "mov {r}, {a}",
            "add {r}, {b}",
            a = in(reg) a,
            b = in(reg) b,
            r = out(reg) result,
        );
    }
    result
}

#[cfg(not(target_arch = "x86_64"))]
fn add_asm(a: u64, b: u64) -> u64 { a + b }

fn main() {
    println!("{}", add_asm(40, 2));
}
```

`asm!` is needed for instructions the compiler doesn't generate on its own: privileged instructions, interrupts, context switches, special barriers. For ordinary computations, optimized Rust code is just as fast.

## SIMD: one instruction, multiple data

Modern processors can process 4, 8 or 16 values in a single instruction. The simplest approach is to let the compiler **auto-vectorize** simple loops. For explicit control, you use the intrinsics from `std::arch`, with runtime detection:

```rust
fn sum_scalar(v: &[f32]) -> f32 {
    v.iter().sum()
}

#[cfg(target_arch = "x86_64")]
fn sum_sse(v: &[f32]) -> f32 {
    use std::arch::x86_64::*;
    let mut acc = [0.0f32; 4];
    let chunks = v.chunks_exact(4);
    let rest: f32 = chunks.remainder().iter().sum();
    // SAFETY: SSE is guaranteed on every x86-64 processor
    unsafe {
        let mut sum = _mm_setzero_ps();
        for c in chunks {
            sum = _mm_add_ps(sum, _mm_loadu_ps(c.as_ptr())); // 4 additions at once
        }
        _mm_storeu_ps(acc.as_mut_ptr(), sum);
    }
    acc.iter().sum::<f32>() + rest
}

fn main() {
    let v: Vec<f32> = (1..=10).map(|x| x as f32).collect();
    println!("scalar: {}", sum_scalar(&v));
    #[cfg(target_arch = "x86_64")]
    {
        println!("SSE: {}", sum_sse(&v));
        println!("AVX2 available: {}", is_x86_feature_detected!("avx2"));
    }
}
```

`std::simd`, a portable variant that works on any architecture, is still unstable. On stable, crates like `wide` or `pulp` offer portable abstractions.

## Check what the compiler generates

At the low level, the real result is the machine code. You can inspect it:

```bash
cargo rustc --release -- --emit=asm      # .s files in target/release/deps
cargo install cargo-show-asm
cargo asm --rust project::sum_scalar     # the assembly of a single function
```

In Rust Playground, the "..." button → **ASM** does the same, and Compiler Explorer (godbolt.org) supports Rust.

> **Key takeaway:** without `std` you provide `#[panic_handler]`, the entry point and, possibly, the allocator yourself. Hardware registers are accessed with `read_volatile` / `write_volatile`. `asm!` inserts instructions directly, and `std::arch` gives SIMD intrinsics, to be used together with `is_x86_feature_detected!`.
