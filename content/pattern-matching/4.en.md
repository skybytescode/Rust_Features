# Pattern matching — Expert

How the compiler checks exhaustiveness, how it translates patterns into code, which new rules the 2024 edition brought, and how patterns interact with types that have no values.

## The exhaustiveness algorithm

The check uses the **usefulness** algorithm (Maranget). For each branch, the compiler asks whether there is any value that matches it and none of the previous branches:

- if there isn't, the branch is **useless**, and the compiler emits the `unreachable_patterns` warning;
- at the end, it asks whether the `_` pattern would still be useful after all branches. If so, the `match` is **not exhaustive**, and the error message shows you a counterexample value.

Guards (`if`) are ignored in this analysis, because the compiler can't prove what result they give.

```rust,compile_fail
fn main() {
    let pair: (bool, Option<u8>) = (true, Some(3));
    match pair {
        (true, Some(_)) => {}
        (false, None) => {}
        (_, Some(0..=9)) => {}
        // error E0004: `(true, None)` and `(false, Some(10_u8..=u8::MAX))` not covered
    }
}
```

## Translation into a decision tree

In MIR, a `match` becomes a series of tests (`switchInt` on the discriminant, comparisons on values and ranges) organized as a **decision tree**. The compiler tries not to test the same thing twice, and guards are evaluated in a guaranteed order: top to bottom, only if the pattern matched.

A semantic detail: a guard sees the bound variables **by reference**, even if the branch moves them. The actual move happens only after the guard passes:

```rust
fn main() {
    let o = Some(String::from("hello"));
    match o {
        Some(s) if s.len() > 3 => println!("long: {s}"), // `s` is moved only if the guard passes
        Some(s) => println!("short: {s}"),
        None => {}
    }
}
```

## 2024 edition: stricter rules for binding modes

When the compiler has automatically stepped into a reference (*default binding mode* `ref`), the 2024 edition forbids writing `ref`, `ref mut`, `mut` or `&` explicitly in that pattern. The combination was confusing, and the rule leaves room for future improvements to match ergonomics:

```rust,compile_fail
fn main() {
    let v = &(1, String::from("a"));
    let (ref a, b) = v; // 2024: error "cannot explicitly borrow within an implicitly-borrowing pattern"
    println!("{a} {b}");
}
```

There are two possible fixes: write the pattern fully explicitly, `let &(ref a, ref b) = v;`, or leave it fully implicit, `let (a, b) = v;`. `cargo fix --edition` does the transformation automatically.

## Types with no values and exhaustiveness

An enum with no variants (or `!`) has no values, so it doesn't need handling. Since Rust 1.82, branches for such types can be omitted when the value is read directly, not through a reference or pointer:

```rust
use std::convert::Infallible;

enum Never {}

fn parse(text: &str) -> Result<String, Infallible> {
    Ok(text.to_uppercase())
}

fn absurd(n: Never) -> u32 {
    match n {} // a match with no branches: there's no value to handle
}

fn main() {
    let Ok(s) = parse("rust"); // no Err branch
    println!("{s}");
    let _ = absurd; // can never be called
}
```

Through a reference (`&Never`), the rule doesn't apply yet. `unsafe` code can create references to invalid memory, so the language doesn't automatically assume that a reference to a type with no values can't exist.

## Patterns on floating-point constants

`f32` / `f64` constants are allowed as patterns, but `NaN` isn't: `NaN != NaN`, so such a pattern would never match. Floating-point ranges are allowed:

```rust
fn classify(x: f64) -> &'static str {
    match x {
        f if f.is_nan() => "NaN",
        ..0.0 => "negative",
        0.0 => "zero",
        0.0..=1.0 => "between 0 and 1",
        _ => "large",
    }
}

fn main() {
    for x in [-1.0, 0.0, -0.0, 0.5, 7.0, f64::NAN] {
        println!("{x}: {}", classify(x));
    }
}
```

`-0.0` matches the pattern `0.0`, because patterns use the IEEE comparison, where `-0.0 == 0.0`. The exclusive range `..0.0` has been stable since Rust 1.80.

> **Key takeaway:** exhaustiveness is checked through "usefulness", without guards. A `match` becomes a decision tree in MIR. The 2024 edition forbids an explicit `ref` under an implicit binding. Types with no values can be left out of a `match` when the value is read directly.
