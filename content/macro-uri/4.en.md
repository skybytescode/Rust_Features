# Macro-uri — Expert

Cum funcționează expansiunea: token trees, ordinea în care se rezolvă macro-urile, igiena prin *span*-uri și regulile de „follow-set” care limitează `macro_rules!`.

## Token trees

Înainte de parsare, codul e transformat în **token trees**: token-uri individuale (identificatori, literali, punctuație) și grupuri delimitate de `()`, `[]` sau `{}`. Un macro primește și produce token trees. De aceea parantezele trebuie să fie mereu echilibrate în intrarea unui macro, chiar dacă restul intrării nu e cod Rust valid:

```rust
macro_rules! ignora {
    ($($t:tt)*) => {};
}

ignora!(asta nu e Rust valid ??? dar parantezele [sunt (echilibrate)]);

fn main() {
    println!("compilat");
}
```

## Ordinea de expansiune

Compilatorul expandează macro-urile **din exterior spre interior** și în mod repetat, până nu mai rămâne niciunul. De aici câteva consecințe:

- un macro primește argumentele **neexpandate**. `macro!(alt_macro!())` vede token-urile `alt_macro ! ()`, nu rezultatul lor;
- `macro_rules!` sunt vizibile textual, de sus în jos, în fișier (*textual scope*), cu excepția celor exportate cu `#[macro_export]` sau importate cu `use`;
- odată ce un fragment a fost capturat ca `expr`, `ty` etc., devine **opac**. Un alt macro nu-l mai poate potrivi cu un literal sau descompune token cu token:

```rust
macro_rules! e_unu {
    (1) => { "unu" };
    ($x:tt) => { "altceva" };
}

macro_rules! trimite_expr {
    ($e:expr) => { e_unu!($e) }; // `$e` e o expresie opacă, nu token-ul `1`
}

macro_rules! trimite_tt {
    ($e:tt) => { e_unu!($e) };   // `$e` rămâne token-ul `1`
}

fn main() {
    println!("prin expr: {}", trimite_expr!(1)); // altceva
    println!("prin tt:   {}", trimite_tt!(1));   // unu
}
```

Cu `$e:tt`, token-ul `1` trece neatins, iar `e_unu!` îl recunoaște.

## Follow-set: ce poate urma după un fragment

Ca macro-urile să rămână valide pe măsură ce limbajul evoluează, după unele fragmente pot urma doar anumite token-uri:

| Fragment | Poate fi urmat doar de |
|---|---|
| `expr`, `stmt` | `=>`, `,`, `;` |
| `pat` | `=>`, `,`, `=`, `|`, `if`, `in` |
| `ty`, `path` | `=>`, `,`, `=`, `|`, `;`, `:`, `>`, `[`, `{`, `as`, `where`, un bloc |
| `ident`, `tt`, `literal` | orice |

```rust,compile_fail
macro_rules! gresit {
    ($a:expr + $b:expr) => { $a + $b }; // eroare: `+` nu poate urma după `expr`
}

fn main() {}
```

## Igiena prin span-uri

Fiecare token poartă un **span**: de unde provine și în ce *context de sintaxă* a fost creat. Igiena lui `macro_rules!` este **mixtă**:

- variabilele locale și etichetele create de macro au contextul macro-ului, deci nu se amestecă cu cele ale apelantului;
- **elementele** (funcții, tipuri, module) și căile se rezolvă în contextul **apelantului**. De aceea un macro exportat trebuie să folosească `$crate::` sau căi absolute (`::std::...`).

Macro-urile procedurale pot alege contextul fiecărui identificator: `Span::call_site()` (ca și cum ar fi scris de apelant), `Span::mixed_site()` (igiena lui `macro_rules!`) sau `Span::def_site()` (instabil, igienă completă).

## Macro-urile procedurale rulează în compilator

Un crate `proc-macro` e compilat pentru platforma **gazdă** și încărcat de `rustc` ca bibliotecă dinamică. Consecințe:

- poate face orice face un program normal (citește fișiere, accesează rețeaua). `sqlx::query!` se conectează chiar la baza de date la compilare. Asta înseamnă și un risc de securitate pentru dependențe necunoscute;
- un panic în macro devine o eroare de compilare. Mesajele bune se emit cu `syn::Error::to_compile_error()` sau `compile_error!`;
- macro-urile procedurale grele (de exemplu `serde_derive` pe sute de tipuri) cresc vizibil timpul de compilare. `cargo build --timings` le arată.

## Vezi ce generează un macro

```bash
cargo install cargo-expand
cargo expand            # tot crate-ul, cu macro-urile expandate
cargo expand modul::fn  # doar un element
```

Pe nightly, `rustc -Z unpretty=expanded` face același lucru, iar `trace_macros!(true);` afișează fiecare pas de expansiune.

## `compile_error!` și diagnostice

Un macro declarativ poate opri compilarea cu un mesaj clar:

```rust,compile_fail
macro_rules! doar_pozitiv {
    (0) => { compile_error!("valoarea trebuie să fie strict pozitivă") };
    ($n:literal) => { $n };
}

fn main() {
    let a = doar_pozitiv!(5);
    let b = doar_pozitiv!(0); // eroare: valoarea trebuie să fie strict pozitivă
}
```

## Macro-uri 2.0

`macro` (fără `_rules!`) este sintaxa „declarative macros 2.0”, încă instabilă. Are igienă completă, vizibilitate ca orice element (`pub macro`) și reguli mai clare. Până la stabilizare, `macro_rules!` rămâne standardul.

> **De reținut:** macro-urile lucrează pe token trees și primesc argumentele neexpandate. Fragmentele capturate (`expr`, `ty`) devin opace. Follow-set-ul limitează ce poate urma după ele. Igiena `macro_rules!` e mixtă, iar macro-urile procedurale rulează cod arbitrar în compilator.
