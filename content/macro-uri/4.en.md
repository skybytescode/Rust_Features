# Macros — Expert

How expansion works: token trees, the order in which macros are resolved, hygiene through *spans*, and the "follow-set" rules that limit `macro_rules!`.

## Token trees

Before parsing, the code is turned into **token trees**: individual tokens (identifiers, literals, punctuation) and groups delimited by `()`, `[]` or `{}`. A macro receives and produces token trees. That's why brackets must always be balanced in a macro's input, even if the rest of the input isn't valid Rust code:

```rust
macro_rules! ignore {
    ($($t:tt)*) => {};
}

ignore!(this is not valid Rust ??? but the brackets [are (balanced)]);

fn main() {
    println!("compiled");
}
```

## Expansion order

The compiler expands macros **from the outside in**, repeatedly, until none are left. A few consequences:

- a macro receives its arguments **unexpanded**. `macro!(other_macro!())` sees the tokens `other_macro ! ()`, not their result;
- `macro_rules!` are visible textually, top to bottom, in the file (*textual scope*), except those exported with `#[macro_export]` or imported with `use`;
- once a fragment has been captured as `expr`, `ty`, etc., it becomes **opaque**. Another macro can no longer match it against a literal or take it apart token by token:

```rust
macro_rules! is_one {
    (1) => { "one" };
    ($x:tt) => { "something else" };
}

macro_rules! pass_expr {
    ($e:expr) => { is_one!($e) }; // `$e` is an opaque expression, not the token `1`
}

macro_rules! pass_tt {
    ($e:tt) => { is_one!($e) };   // `$e` stays the token `1`
}

fn main() {
    println!("through expr: {}", pass_expr!(1)); // something else
    println!("through tt:   {}", pass_tt!(1));   // one
}
```

With `$e:tt`, the token `1` passes through untouched, and `is_one!` recognizes it.

## Follow-set: what can come after a fragment

So that macros stay valid as the language evolves, only certain tokens can follow some fragments:

| Fragment | Can only be followed by |
|---|---|
| `expr`, `stmt` | `=>`, `,`, `;` |
| `pat` | `=>`, `,`, `=`, `|`, `if`, `in` |
| `ty`, `path` | `=>`, `,`, `=`, `|`, `;`, `:`, `>`, `[`, `{`, `as`, `where`, a block |
| `ident`, `tt`, `literal` | anything |

```rust,compile_fail
macro_rules! wrong {
    ($a:expr + $b:expr) => { $a + $b }; // error: `+` can't follow `expr`
}

fn main() {}
```

## Hygiene through spans

Each token carries a **span**: where it comes from and in which *syntax context* it was created. The hygiene of `macro_rules!` is **mixed**:

- local variables and labels created by the macro have the macro's context, so they don't mix with the caller's;
- **items** (functions, types, modules) and paths are resolved in the **caller's** context. That's why an exported macro must use `$crate::` or absolute paths (`::std::...`).

Procedural macros can choose the context of each identifier: `Span::call_site()` (as if written by the caller), `Span::mixed_site()` (the hygiene of `macro_rules!`) or `Span::def_site()` (unstable, full hygiene).

## Procedural macros run inside the compiler

A `proc-macro` crate is compiled for the **host** platform and loaded by `rustc` as a dynamic library. Consequences:

- it can do anything a normal program does (read files, access the network). `sqlx::query!` actually connects to the database at compile time. That also means a security risk for unknown dependencies;
- a panic in a macro becomes a compile error. Good messages are emitted with `syn::Error::to_compile_error()` or `compile_error!`;
- heavy procedural macros (for example `serde_derive` on hundreds of types) noticeably increase compile time. `cargo build --timings` shows them.

## See what a macro generates

```bash
cargo install cargo-expand
cargo expand            # the whole crate, with macros expanded
cargo expand module::fn # just one item
```

On nightly, `rustc -Z unpretty=expanded` does the same, and `trace_macros!(true);` prints each expansion step.

## `compile_error!` and diagnostics

A declarative macro can stop compilation with a clear message:

```rust,compile_fail
macro_rules! positive_only {
    (0) => { compile_error!("the value must be strictly positive") };
    ($n:literal) => { $n };
}

fn main() {
    let a = positive_only!(5);
    let b = positive_only!(0); // error: the value must be strictly positive
}
```

## Macros 2.0

`macro` (without `_rules!`) is the "declarative macros 2.0" syntax, still unstable. It has full hygiene, visibility like any item (`pub macro`) and clearer rules. Until it's stabilized, `macro_rules!` remains the standard.

> **Key takeaway:** macros work on token trees and receive their arguments unexpanded. Captured fragments (`expr`, `ty`) become opaque. The follow-set limits what can come after them. `macro_rules!` hygiene is mixed, and procedural macros run arbitrary code inside the compiler.
